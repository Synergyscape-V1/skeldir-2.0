# B2.5-P13 Independent Production Topology Reproduction

This runbook lets an auditor who does not trust engineering provision and
observe the load-bearing Bayesian production topology from a clean clone. It
uses the exact production Bayesian Dockerfile, its unmodified default Celery
command, distinct execution and dispatch-publisher database principals, a real
PostgreSQL 15 broker/backend, real four-chain PyMC sampling, and the positive
Trust composition journey.

## Supported reproduction host

The authoritative path is Ubuntu 22.04/24.04 x86-64 with:

- Docker Engine with host networking;
- PostgreSQL `psql` client 15 or later;
- Python 3.11;
- repository dependencies from `backend/requirements.txt` and
  `backend/requirements-dev.txt`.

Docker Desktop 4.34+ can also execute the path when host networking is enabled.
The minimal `docker-compose.local.yml` remains intentionally outside P13
evidence because it does not provision the two production worker identities.

## Clean-clone execution

From the repository root:

```bash
python -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade pip
pip install -r backend/requirements.txt -r backend/requirements-dev.txt

docker run -d --rm --name skeldir-c16-postgres \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=postgres \
  -p 55432:5432 postgres:15-alpine

until PGPASSWORD=postgres psql \
  postgresql://postgres@127.0.0.1:55432/postgres \
  -tAc 'select 1' >/dev/null 2>&1; do sleep 1; done

scripts/ci/run_b25_p13_c16_production_topology_proof.sh \
  | tee /tmp/b25-p13-c16-production-topology.log
```

On completion, remove the disposable database:

```bash
docker rm -f skeldir-c16-postgres
```

The proof script is fail-closed. It performs all of the following rather than
asking the auditor to infer them from configuration:

1. provisions `migration_owner`, `app_user`, `app_worker`, and
   `app_dispatch_publisher`, then replays Alembic to head;
2. asserts the worker is neither superuser nor `BYPASSRLS`;
3. builds `backend/Dockerfile.bayesian` without modification and records the
   image content id and default command;
4. traces the image-owned governed dependency closure;
5. runs real PyMC sampling twice and observes four sequential chains, 4000
   posterior draws, zero divergences, and no identical chain pair;
6. observes the runtime policy's four-chain/one-core/one-BLAS-thread
   containment from inside that image;
7. starts the image's default execution worker and a separate publisher worker
   with their distinct database credentials;
8. starts the real beat scheduler, drives the positive confidence/Trust journey,
   and requires both the publisher and execution task names in their independent
   container logs;
9. prints `B25_P13_C16_PRODUCTION_TOPOLOGY_PASS` only after every observation.

## Boundaries

This proves the repository's production artifact/process/database topology and
its persisted posterior-to-Trust composition. It does not prove a particular
cloud provider's network, IAM, autoscaling, DNS, or secret-manager deployment.
Those hosted controls cannot be reproduced by a clean-clone script without
granting the auditor production authority; absence of that claim is explicit.
