# Webhook Replay And Diagnosis

Webhook replay in M4 is local fixture replay only. It uses the existing FastAPI
webhook endpoint, tenant key resolver, and provider signature verifier. No
production replay endpoint exists or is added.

## Commands

Seed local-only tenant, secret, and replay fixture material.

```yaml
command: make ops-seed-diagnostics
execution_context: container_api
command_class: local_fixture_replay
requires_seeded_fixture: false
mutates_state: local_fixture_only
tenant_scope_required: false
idempotency_sensitive: true
signature_sensitive: true
```

Replay valid, tampered, and duplicate controls through the container network.

```yaml
command: make ops-webhook-replay-local
execution_context: container_network_curl
command_class: local_fixture_replay
requires_seeded_fixture: true
mutates_state: local_fixture_only
tenant_scope_required: true
idempotency_sensitive: true
signature_sensitive: true
```

The executable replay script validates `--api-base-url` and `OPS_API_BASE_URL`
before sending any request. It allows only local HTTP targets such as
`http://api:8000`, `http://localhost:<port>`, or `http://127.0.0.1:<port>`.
It hard-fails on `https://*`, production/staging domains, and arbitrary external
hosts with the message that production payload replay is forbidden in M4.

Trace downstream B2.3 dispatch after successful ingress.

```yaml
command: make ops-b23-trace
execution_context: container_api
command_class: read_only_inspection
requires_seeded_fixture: true
mutates_state: false
tenant_scope_required: true
idempotency_sensitive: false
signature_sensitive: false
```

## Authenticity Boundary

Provider authenticity is owned by `backend/app/api/webhooks.py` and
`backend/app/webhooks/signatures.py`. Tenant selection requires
`X-Skeldir-Tenant-Key`, resolved through
`security.resolve_tenant_webhook_secrets`. Stripe, Shopify, and WooCommerce use
HMAC. PayPal uses RSA certificate verification with testing override support in
the existing verifier.

The local replay fixture uses a run-scoped Stripe signing secret generated by
`make ops-seed-diagnostics` and stored under `.tmp/m4_ops/`. No committed
production-like secret is used.

## Positive And Negative Controls

| Fixture | Expected |
| --- | --- |
| `m4-webhook-valid` | Valid Stripe HMAC request returns success or idempotent success through the real endpoint. |
| `m4-webhook-tampered` | Tampered signature returns unauthorized and does not create a canonical event. |
| `m4-webhook-duplicate` | Reusing the same run-scoped idempotency key leaves canonical event count unchanged after the first accepted replay. |

## Correlation Path

After a valid replay:

1. Inspect API response `event_id` and `idempotency_key`.
2. Query `webhook_ingress_identities` through `make ops-b23-trace`.
3. Confirm `verified_commerce_ingress_state = authenticity_verified`.
4. Confirm `b23_match_task_dispatches.task_name = app.tasks.revenue_verification.execute_b23_batch_match_engine`.
5. If dispatch exists but no verdict appears, switch to [B2.3 match diagnosis](b23_match_diagnosis.md).
6. If dispatch does not exist, inspect API logs and [DLQ](dlq_inspection_and_replay.md).

## Failure Branches

| Failure | Meaning | Next step |
| --- | --- | --- |
| 401 unauthorized | Tenant key missing/unknown or signature invalid. | Check tenant fixture and signature header. |
| `dlq_routed` | Auth succeeded but payload failed schema or validation. | Inspect dead event by correlation ID and payload class. |
| Success but no B2.3 dispatch | Ingress identity missing, unsupported family, or natural dispatch disabled. | Run `make ops-b23-trace`, then inspect logs. |
| Duplicate response | Idempotency path engaged. | Confirm canonical row count did not increase. |

## Non-Replayable Payload Classes

Never replay production provider payloads from logs, DLQ rows, task kwargs, or
operator notes. Never replay payloads containing uncertain PII stripping state.
Never replay when tenant identity, signature material, or idempotency key origin
is unknown.

## Safety Warnings

M4 replay is not a production incident mechanism. It is a local signed fixture
that proves the existing authenticity and idempotency path remains diagnosable.
Do not disable auth checks, do not alter signature verification, do not commit
secrets, do not reuse production idempotency keys, and do not override the local
API base URL to a non-local target.
