partially confirmed.

schema and as the published success-response schema, so correcting the runtime
protocol in the third P11 corrective left the contract silently behind.

This is the general shape of P12-H01: proof optimized per implementation unit,
with no owner for composition.

## 8.3 What is genuinely NOT complete

One item remains, and it is not an engineering gap. It cannot be closed by any
change to this repository.

### The dedicated context is not a *required* check

`B2.5-P12 CI Gates` exists, runs, and passes. It does not **block**. Adding a
required status check is a branch-protection setting — a repository
administration act, outside the authority of anything in the tree.

The registry states the two facts as separate fields precisely so no reader can
collapse them:

```yaml
dedicated_p12_context_present:                       true
dedicated_p12_context_required_in_branch_protection: false
```

Practical consequence, stated plainly: **a future PR that deletes
`b2_5-p12-ci-gates.yml` would not be blocked by branch protection**, even though
the gate exists and is green today. What still blocks is the P11 binding, which
is why §8.1 retains it.

### This was proven, not assumed — by breaking it

The required-status-check contract at
`contracts-internal/governance/b03_phase2_required_status_checks.main.json` was
edited to list `B2.5-P12 CI Gates`. That edit was wrong, and CI said so:

```text
required status checks enforcement failed: missing contexts
actual contexts:
##[error]Process completed with exit code 1.
```

`enforce_required_status_checks.py` validates that contract against **live
branch protection**. A contract file cannot make a context required; it can only
describe what already is. Listing an unenforced context made the contract assert
something false, and `Governance Guardrails` failed — correctly.

The entry was reverted. The contract will list this context only after branch
protection carries it, at which point the enforcer will pass on it.

This is the strongest available evidence for the §26 distinction: the governance
layer detected an author of this very phase overclaiming enforcement, and refused
the merge. The boundary between *governance configuration* and *CI technical
proof* is not a rhetorical caveat in this pack — it is a gate that fired.

### To finish

A single administrative action, by a repository administrator:

> Settings → Branches → `main` → Require status checks → add **`B2.5-P12 CI Gates`**

Then add the same string back to the required-checks contract, where
`enforce_required_status_checks.py` will then validate rather than reject it.

## 8.4 CI incidents on the P12 PR

Three failures occurred. All three are recorded, including the reasoning that
initially mis-attributed them, because this program's failure mode is exactly
"conclusion stated before evidence read".

### Docker Hub 500s (two failures, infrastructure)

`b07_phase8_closure_pack` and `Phase 8 Regression Gate (Full Physics)`:

```text
ERROR: unexpected status from HEAD request to
https://registry-1.docker.io/v2/library/python/manifests/3.11-slim:
500 Internal Server Error

postgres Error received unexpected HTTP status: 500 Internal Server Error
```

Docker Hub image pulls, before any test executed. Reran on the identical commit;
no code, threshold or gate changed in response.

### Mis-attribution, corrected

On first sight all three had passed on the baseline `7d8f4824f`, and that was
taken as evidence this corrective caused them. Reading the logs refuted it for
two of the three.

Workflow history distinguishes *pre-existing* from *new*. It does not
distinguish *my defect* from *the world's*: a transient outage produces exactly
the same signature as a real regression. Only the failing step distinguishes
them, and that step must be read before a cause is named.

### `B2.4-P9 Worker Tenant Hygiene Proof` (one failure, flaky)

60 passed, 1 failed:

```text
FAILED test_b24_p9_pool_poison_is_closed_and_replaced_without_manual_reset
  assert datetime(2026, 8, 10, 16, 11, 34, ...) is None
```

The assertion is `state["xact_start"] is None` inside
`_assert_backend_absent_or_not_idle_in_transaction`, which reads
`pg_stat_activity` to confirm an old PostgreSQL backend is gone or not
idle-in-transaction. A briefly non-null `xact_start` is a backend-teardown race
against a live database.

Attribution evidence, not assertion: this corrective's diff touches zero files
under `backend/app/bayesian/**`, worker, DB-session, Celery or pooling paths. It
changes contract schemas, three new CI validators, governance registries and
allowlists. There is no causal route from those to a PostgreSQL backend teardown
timing window.

Classified as a pre-existing flaky test surfaced by this run, not a regression
introduced by it. Recorded rather than silently reran.

### `b057_p5_full_chain_e2e` (one failure, race — mechanism identified)

On the workflow PR at `7fdf0bcc1`:

```text
assert deltas["celery_task_success_total_matview_refresh_all_for_tenant"] >= 1
E       assert 0.0 >= 1
```

The prior of innocence was weak here and is worth stating: this workflow had **24
consecutive successes across every branch**, and the only failure was on my
commit. That pattern normally indicts the change. It was investigated on that
basis rather than waved off.

**Diff scope.** `117064be2 → 7fdf0bcc1` is two files: one line removed from a
governance JSON, twelve comment/field lines added to a docs YAML. Zero backend
files. Neither file is referenced by the test or by its workflow. No causal route
exists.

**Mechanism, from the repository's own documentation** rather than inference —
`backend/app/observability/metrics.py:18` records that worker counters are
written into Prometheus multiprocess shards and that "the worker metrics exporter
aggregates them via `MultiProcessCollector`". The repo further ships
`multiproc_orphan_files_detected` and `multiproc_pruned_files_total` with an
explicit pruning grace window for shards owned by non-live PIDs. A worker process
that exits between task completion and the scrape can therefore have its
increment aggregated late, or pruned, while the database effect it already
committed stays plainly visible.

That is exactly the observed signature: the functional assertion
`total_allocated_cents == 1050` **passed** earlier in the same test, so the
refresh demonstrably ran. Only its counter read zero.

**Structural confirmation.** The test polls for eventual consistency everywhere
except the assertion that failed:

| Observation | Read strategy |
| --- | --- |
| `job_row`, `allocation_count`, `matview_row` (DB) | `_poll_until`, retried to a deadline |
| worker metrics (line 813) | `_scrape_metrics`, single shot |

**Empirical discriminator.** Re-run of the identical SHA `7fdf0bcc1`, no code
change: `attempt=2 → success`. Same input, opposite outcome. This is the datum
that separates nondeterminism from defect, and it is the reason the failure is
classified rather than merely argued away.

**Not absorbed.** The defect belongs to B0.5.7-P5, not P12. Widening this phase
to repair an unrelated test would be scope drift of the kind §28 forbids. The fix
is recorded instead: wrap the four metric-delta assertions in the `_poll_until`
helper the test already defines, so the counter read tolerates the same eventual
consistency its database reads already do.

A re-run was used to obtain a green result. That is legitimate only because the
same-SHA experiment established nondeterminism *first*; re-running until green
without that proof would be indistinguishable from concealing a regression.

### Why this is NOT COMPLETE rather than COMPLETE

Every technical gate is satisfied. The dedicated context exists, its trigger
paths are complete, it ran green on the exact main lineage, and eleven of its
negative controls fired there. The engineering has no known remaining gap.

It is still recorded as NOT COMPLETE, against the directive's own anti-gaming
criterion:

> A workflow that exists but is not enforced is NOT completion.

That criterion is dispositive. Deleting `b2_5-p12-ci-gates.yml` in a future PR
would not be blocked today. Until `B2.5-P12 CI Gates` is a required status check,
the gate is advisory in the only sense that matters — its absence would not stop
a merge.

The temptation here is to report completion on the strength of a green mainline
run and treat the branch-protection setting as an administrative footnote. That
would be precisely the overclaim this phase was created to make impossible, and
the pack would then be an instance of the failure mode it documents.

**Remaining work: one administrative action, listed in §8.3. No code.**

Final adjudication belongs to an independent audit.
