## 2. P12-P0 proof

### 2.1 Original reproduction on protected main

The directive required exercising the real production path rather than reading a
fixture. Executed against `7d8f4824f`:

```text
ACTUAL RESPONSE vs PUBLISHED 200 SCHEMA: 3 error(s)
  - artifact_schema_version:  'b25-p11-export-artifact-v1' was expected
  - artifact_signing_domain:  'skeldir:b25-p11:export-artifact:v1\0' was expected
  - canonicalization_version: 'b25-p11-artifact-framing-v1' was expected

P12-H00: CONFIRMED
```

### 2.2 Root cause

Root-cause hypothesis 4 from the directive is confirmed, and hypothesis 2 is
partially confirmed.

Existing validators proved two disjoint statements — *the manifest says v2* and
*the v1 example validates against the v1 schema* — and never the composition
*the live response validates against the schema resolved from the OpenAPI*.
`export-artifact.v1.yaml` was simultaneously serving as historical protocol
schema and as the published success-response schema, so correcting the runtime
protocol in the third P11 corrective left the contract silently behind.

This is the general shape of P12-H01: proof optimized per implementation unit,
with no owner for composition.

## 8. What is NOT complete, and why

Stated at full strength rather than as a footnote.

### 8.1 No dedicated `B2.5-P12 CI Gates` context

Creating `.github/workflows/b2_5-p12-ci-gates.yml` requires the `workflow` OAuth
scope. Both available credentials carry `gist, read:org, repo`. The push is
rejected at the GitHub API boundary; no repository change can work around it.

The workflow was written and validated locally, then withheld from the commit
and retained outside the repository for application with a scoped token.

**Leaving the proofs unbound was not acceptable** — an uninvoked validator is
precisely the vacuous proof this phase exists to eliminate. So the composition
proofs are invoked from `validate_b25_p11_export_compatibility.py`, inside
`B2.5-P11 Export Compatibility`, which is already a required status check on
protected main.

Consequences, kept distinct:

| Property | State |
| --- | --- |
| A composition regression turns a required check red today | **yes** |
| A dedicated P12 gate identity exists | **no** |
| P12-G5 (branch-protection eligibility) satisfiable | **no** |
| P12-G10 (dedicated P12 context on exact lineage) satisfiable | **no** |

Enforcement strength and gate identity are different claims. Only the first is
achieved.

### 8.2 Three path-trigger gaps

All six load-bearing production paths reach at least one required B2.5 workflow.
The three P12 validator scripts reach none, because adding trigger paths also
requires `workflow` scope. They are enumerated in `path_trigger_known_gaps` with
reasons and enforced by Plane D.

Practical effect: editing *only* a P12 validator would not trigger the bound
context. Editing anything it guards still runs it.

### 8.3 Consequent verdict

**P12-P0: PASS.** **B2.5-P11: COMPLETE.**

**B2.5-P12: NOT COMPLETE**, blocked on P12-G5 and P12-G10 by a missing OAuth
scope. Per directive §21, claiming completion while a required gate is
unsatisfied would be exactly the overclaim this program forbids — and per §26,
governance configuration and CI technical proof must never be represented as one
another.

To finish: apply the retained workflow with a `workflow`-scoped token, add the
three validator paths to its triggers, then re-run the dedicated context on the
exact main lineage.
