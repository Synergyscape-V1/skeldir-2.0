# B2.3-P4 Remediation Evidence Pack

Date: 2026-05-06

Branch: `codex/b23-p4-queue-performance-lock`

Scope: Phase B2.3-P4 only. No P5/P6/B2.4/B2.6/dashboard/frontend/LLM explanation work was added.

## Initial Findings

- B2.3 revenue verification tasks were routed through the maintenance queue, not a dedicated B2.3 worker queue.
- The Procfile and E2E worker topology had no B2.3-only worker.
- P3 transition tasks were registered, but inherited maintenance routing rather than isolated B2.3 routing.
- The database session layer had one shared SQLAlchemy engine and no B2.3 bounded pool.
- No canonical P4 SQL telemetry surfaces existed for match rate, DLQ depth, or webhook failure counts.
- No P4 governance contract or negative-control enforcer existed.
- The production benchmark path needed a bounded set-based micro-batch entry point with real Postgres plan evidence.

## Remediations

- Added canonical queue `b23_match_engine` and routed all `app.tasks.revenue_verification.*` tasks to it.
- Added a B2.3-only worker command in `Procfile` and `docker-compose.e2e.yml`.
- Added dedicated B2.3 SQLAlchemy engine/session with bounded pool size, overflow, acquisition timeout, statement timeout, and lock timeout.
- Routed P3 pending-to-unmatched and provisional-to-confirmed transition task execution through B2.3 DB sessions.
- Added `execute_b23_batch_match_engine` production entry point and Celery task wrapper.
- Implemented bounded micro-batch execution using `FOR UPDATE OF wi SKIP LOCKED`, materialized row claiming, bulk verdict upsert, and short per-chunk transactions.
- Moved candidate matching to the durable `attribution_commerce_identities` substrate to preserve typed-boundary authority.
- Added P4 access-path indexes for verdict lookup, claim ordering, attribution event joins, telemetry match rate, DLQ depth, and webhook failure telemetry.
- Added canonical SQL telemetry under `docs/ops/b23_p4/sql/`.
- Added `contracts-internal/governance/b23_p4_queue_performance.main.json`.
- Added `scripts/ci/enforce_b23_p4_queue_performance.py` and negative-control tests.
- Wired P4 static, negative-control, and runtime DB proofs into `.github/workflows/ci.yml`.

## P4 Gate Evidence

- Dedicated queue: `b23_match_engine`.
- Worker isolation: B2.3 worker consumes only `b23_match_engine`.
- DB pool protection: B2.3 uses `b23_engine`/`get_b23_session` with bounded pool and fail-fast acquisition.
- Transition binding: P3 transition tasks remain in beat schedule and route via B2.3 queue.
- Benchmark scope: runtime test seeds tenant, exactly 1,000 eligible records, background non-eligible rows, and `ANALYZE` before timing.
- Timed region: only `execute_b23_batch_match_engine(...)`.
- Batch result: 1,000 processed, 2 chunks of 500, duration under 10 seconds in local runtime proof.
- Query count: bounded by chunk count, not record count.
- Lock footprint: each chunk uses `FOR UPDATE OF wi SKIP LOCKED LIMIT :chunk_size`; no 1,000-row monolithic transaction.
- Planner evidence: runtime tests execute `EXPLAIN (ANALYZE, BUFFERS)` for candidate and telemetry paths.
- SQL telemetry: all three canonical SQL files execute directly against Postgres.
- Negative controls: P4 enforcer tests cover missing route, forbidden worker overlap, missing pool, N+1 token, and missing telemetry index.
