```text
        ↓

        ↓

        + exact artifact lifecycle

        ↓

        ↓

        ↓

```

The ownership boundary is deliberate. B2.4 computes and persists confidence;
B2.5 validates that persisted state and explains it in a signed envelope. Trust
does not call the classifier, aggregate financial facts, select a latest fit,
fit a model, dispatch work, repair diagnostics, mutate lifecycle state, or call
an LLM. Only pre-existing governed security/audit writes remain on the request
journey.

Historical fit rows are not backfilled with reconstructed classifications.
Their new columns remain null and therefore project
`persisted_classification_missing`. Fabricating historical inputs would be less
truthful than an explicit unavailable state. The migration downgrade is marked
destructive because dropping persisted classification context loses evidence
that cannot be reconstructed exactly; ADR-016 records that boundary.

### 3. Final subject and authority architecture

`match_verdict` remains the singular event-level deterministic attribution fact.
B2.4 confidence is not silently attached to that fact. It is a separate signed
`confidence_projection` subject whose identity names one exact persisted fit.
This prevents an envelope from implying that an event verdict and a Bayesian
fit share identity, lifecycle, or observation time when they do not.

The read topology is:

```text
machine credential
  -> production authenticate / scope / replay / rate controls
  -> tenant-bound SQLAlchemy session and PostgreSQL RLS GUC
  -> exact match-verdict source + exact confidence-projection source
  -> production TrustEnvelope builder
  -> autonomous audit persistence
  -> Ed25519 signing
  -> exact HTTP response bytes
  -> governed JWKS HTTP fetch
  -> independently reconstructed public-key-only registry
  -> verification of the exact received envelopes
```

The confidence read model is read-only. It does not enqueue work, invoke a
Bayesian model, repair diagnostics, revive artifacts, choose a “latest” fit, or
mutate B2.3/B2.4 authority tables. Monetary data remains integer cents; a
multi-currency fit window fails closed rather than inventing an aggregate.

### 14.2 CONFIRMED DEFECT — the confidence contract is wider than the runtime

This section previously recorded the B2.4 degradation states as "unreachable"
and left open whether that was correct design. **That question has been answered
authoritatively, and the answer makes this a defect rather than a boundary.**

The governing answer:

> TrustEnvelopes should carry B2.4 confidence metadata — but only as subordinate,
> explicitly typed metadata around deterministic truth. TrustEnvelope always
> carries an explicit confidence state; it carries numerical/interval confidence
> only when B2.4 has a valid, diagnostics-permitted result. B2.4 enriches
> deterministic truth but can never gate, override, or recreate it.

### The measured gap

`contracts/trust-api/confidence-metadata.schema.json` publishes:

| Field | Permitted | Runtime emits | Unreachable |
| --- | --- | --- | --- |
| `confidence_status` | available, unavailable, degraded, diagnostics_failed | `unavailable` | 3 |
| `confidence_authority` | deterministic_only, b24_confidence_projection, explicitly_unavailable | `deterministic_only` | 2 |
| `diagnostics_status` | passed, failed, not_applicable, unavailable | `not_applicable` | 3 |
| `unavailable_reason` | cold_start_insufficient_data, diagnostics_failed, artifact_pruned, source_snapshot_stale, model_not_fit, not_applicable, null | `not_applicable` | 6 |


**14 of 18 published values are unreachable.** `app.trust.builder._confidence_unavailable()`
returns a constant and the builder consumes no B2.4 source, so the contract
promises a capability the runtime cannot deliver.

Note the `unavailable_reason` enum contains exactly the degradation states the
directive asked P13 to seed — `diagnostics_failed`, `artifact_pruned`,
`source_snapshot_stale`. They are first-class contract values, not missing
fixtures. And the emitted `not_applicable` is semantically wrong under the
governing answer: it says *no confidence concept applies*, where the truth is
*confidence is absent for a reason* (`cold_start_insufficient_data`).

### Why this is the P12-P0 defect class

Published contract and runtime behaviour diverge, and every phase-local validator
passes because each half is internally consistent. That is precisely the shape
P12-P0 closed for the artifact protocol, in a different field.

### The isolation tension, and how it is resolved

Closing this defect is not a matter of wiring an existing function into the
builder. The confidence semantics are already fully specified by
`app.bayesian.confidence_policy.classify_confidence()`, a complete state machine
mapping snapshot mismatch, missing fit, fallback, fit failure, diagnostics,
interval status and artifact lifecycle onto exactly the enum values the contract
publishes. Nothing needs inventing.

The obstacle is that it lives in `app.bayesian`, which is a **forbidden module
for the trust path** under B2.5-P12 isolation — enforced by `NC-P12-ISO-01` and
the transitive import graph hardened during P13-P0. Two invariants this program
holds are therefore in direct tension:

```text
P12 isolation   the trust path must not reach app.bayesian
§46 confidence  envelopes must carry B2.4 confidence, read-only
```

**Resolution, decided by the architecture owner:**

> B2.4 persists its already-classified confidence state to a tenant-scoped
> surface. The trust builder reads a **state**, not a policy — the same shape as
> `MatchVerdictSource`.

This preserves the isolation boundary exactly as written rather than moving it,
keeps a single owner for the classification rules, and introduces no duplicated
financial-trust semantics. The rejected alternatives are recorded because the
reasoning matters: relocating the policy to a neutral module would move the P12
boundary and require the forbidden-prefix set to be re-reasoned; duplicating the
rules trust-side would create two copies of financial-trust semantics that can
silently diverge, which is the exact composition-failure class P13 exists to
detect.

### Scope

P13 **proves** this composition failure; it does not repair it. Implementing B2.4
confidence projection means reading fits, diagnostics, artifact lifecycle and
snapshot staleness — a B2.4-integration change, not an E2E-harness change, and
§2091 forbids P13 creating new TrustEnvelope semantics.

Recommended as the **B2.5-P14 mandatory entry gate**, following the pattern this
program has now used twice: the defect stays owned by the earlier invariant and
is repaired as the entry condition of the next cycle. The reachable count is
pinned in CI, so implementing the projection turns this proof red and forces the
evidence to be revisited rather than silently aging.

### 14.3 The float-money scenario is not representable, and that is stronger

This was recorded as "G6 proven at the boundary, not through the route".
Attempting the route-level fixture showed why it cannot be built.

Every minor-unit column on the authoritative source table is `integer NOT NULL`:

```text
attributed_amount_minor                :: integer NOT NULL
canonical_captured_gross_amount_minor  :: integer NOT NULL
canonical_expected_gross_amount_minor  :: integer NOT NULL
canonical_net_verified_amount_minor    :: integer NOT NULL
discrepancy_amount_minor               :: integer NOT NULL
verified_amount_minor                  :: integer NOT NULL
```

A float cannot be stored — PostgreSQL coerces at insert — and the value can never
be absent. So the "legacy float-only money source" the directive posits cannot
reach the route, because it cannot exist in the source table.

G6 therefore proves two things rather than one:

1. **behavioural** — `resolve_authoritative_money` refuses a float with a typed
   reason code and `amount_minor is None`, never coercing;
2. **structural** — the source schema forbids the scenario outright, asserted
   directly against `information_schema` rather than simulated with a row the
   database would refuse.

The second is the stronger guarantee: money authority is enforced by the schema,
not only by application code. A fixture would have demonstrated less, and could
only have been built by first weakening the column.

### 14.4b The harness was running as a superuser, and RLS was inert

This is the most serious defect found in the harness, and it was the author's.

`app.trust.tenant_security` refuses any connection whose role has

A superuser has that attribute. So every journey that overrode the

least-privilege identity and pass. The results stand, but they stand on a

## 15. Recommended B2.5-P14 mandatory entry gate

This program has now used the same pattern twice — P12-P0 closed P11's
contract-projection defect, P13-P0 closed P12's proof-integrity defects. The
defect stays owned by the earlier invariant and is repaired as the entry
condition of the next cycle. The same shape applies here.

### 15.1 Objective

Make the runtime capable of emitting every confidence state its published
contract permits, without breaching trust-path isolation.

### 15.2 Required work, in dependency order

1. **B2.4 persistence surface.** A tenant-scoped table carrying the *classified*
   output of `classify_confidence()` — status, authority, diagnostics status,
   unavailable reason, model type, model version, score basis points, and the
   source-window identity the classification applies to. Written by B2.4 where it
   already classifies; never written by the trust path.
2. **Trust-side source adapter.** A read-only adapter in
   `app.trust.source_adapters` reading that surface, shaped like
   `MatchVerdictSource`. It must not import `app.bayesian`, and `NC-P12-ISO-01`
   must continue to fire if it ever does.
3. **Builder consumption.** `_confidence_unavailable()` is replaced by a
   projection of the adapter's state, preserving the sovereign rules: the
   deterministic amount stays authoritative when confidence is absent, no
   interval is ever fabricated, and **a read must never trigger a fit** — P13-G8
   already proves the last of these and must keep passing.

### 15.3 An open semantic question that must be answered first

B2.4 confidence is **source-window scoped**; a TrustEnvelope subject is
**verdict scoped**. How a single match verdict maps onto the window whose
confidence applies to it is a design decision, not an implementation detail, and
it is not answered anywhere in the current corpus. Implementing before that is
settled would mean inventing the mapping in the financial-trust path.

### 15.4 Falsifiers the entry gate must carry

```text
NC-P14-01  a fabricated interval survives failed diagnostics
NC-P14-02  a trust read triggers a Bayesian fit
NC-P14-03  confidence absence is reported as not_applicable rather than a reason
NC-P14-04  the trust path imports app.bayesian          (inherited NC-P12-ISO-01)
NC-P14-05  deterministic revenue is gated by confidence availability
```
