## 1. The finding both audits reached, by different routes

Two auditors examined B2.5-P13 independently and converged on one conclusion.
Neither said that a proof was wrong. Both said that the proofs **did not touch**.

C7 closed source causality: a committed financial mutation appends dirty
evidence in the same transaction, and no future writer can bypass it. C1–C6
closed the Trust boundary: a confidence projection is signed, tamper-evident,
and verifiable against a published JWKS. Between those two closed halves sat a
seam that neither suite crossed — and across that seam, the model identity
changed.

The invalidation triggers emitted `model_type='mmm'`. The Trust confidence
projection accepts only `model_type='bayesian_attribution_confidence'`. The
value produced by one half was, by construction, refused by the other.

The consequence is not a degraded result. It is that **no financial source
change in the system's history could ever have reached a signed Trust
envelope**, and no gate in the repository was capable of observing that. Each
suite passed because each suite supplied its own starting authority: the
causality suite ended at a dirty row it never asked anyone to consume, and the
Trust suite began at a fit row it wrote itself.

This is the failure mode the C7 report should have anticipated when it recorded
C7-J as PARTIAL. The gap it named was transport. The gap that mattered was
conduction.

Each was reproduced against live PostgreSQL 15 running the repository's own
unmodified code before anything was changed.

|----|---------|-------|

| **F-02** | Staleness required **exact** window equality. A change inside a wider fit's window could not stale it. Two of the three production dirty producers forward arbitrary caller windows, so neither could ever invalidate anything. | Dispositive |
| **F-03** | Staleness re-joined on `model_version`. A fit produced by an earlier pipeline version became permanently unstaleable — the more out of date it was, the safer it was. | Dispositive |

F-05 and F-06 deserve emphasis. Neither was visible from either audit, from the
shipped source, or from any existing gate. Both became visible the moment a real
source change was required to reach a signed envelope without anyone helping it
along — which is precisely the argument for building the contiguous journey
rather than adding another segment proof.

F-06 in particular was invisible to every form of inspection this repository
performs. The task exists, so a registry check passes. It is routed through a
durable outbox and dispatched to the `bayesian` queue, so a transport check
passes. It returns without raising, so a liveness check passes. It is retried on
a schedule, so a recovery check passes. Only asking the whole chain to produce a
fit reveals that the table it consults has no writer outside the test suite —
and that every existing proof of a fit supplied that row itself.

### A scope call that was made, and then corrected

When F-06 was first found it was recorded as **open and out of scope**, on the
reasoning that building a feature-authority producer meant deciding how counts
are computed and how freshness is versioned — a modelling deliverable rather
than a corrective action on identity and window causality.

That reasoning was wrong about Skeldir, and the correction is worth stating
because it is the difference between a real scope boundary and an imagined one.
Feature authority was never supposed to decide whether data is trustworthy. It
measures the shape of an already-defined snapshot so that two policies which
**already exist** can make their decisions:

```
minimum sufficiency   b24-eligibility-v1      already decided
        |
        v
source shape          feature authority       the missing piece
        |
        v
maximum complexity    b24-resource-policy-v1  already decided
```

Nothing needed inventing. Every threshold, every cap, every membership rule and
even the bounded counting discipline were already governed and versioned. The
absence of a writer was an integration defect wearing the costume of a design
question. F-06 is remediated in §3.

The distinction that matters, and that the remediation preserves: *changing*
those thresholds — asking whether twenty events is really enough, or whether
channel diversity should outweigh event count — would be a new modelling phase,
and none of it happens here.

## 3. Remediations

### F-01 — one governed identity space

`backend/app/bayesian/model_identity.py` is now the single registry of model
identities. It separates the two things that had been conflated:

- `model_type` — the statistical model family. This is what carries identity
  across the pipeline and what Trust projects.
- `model_version` — the pipeline version that produced a fit. Provenance
  metadata, never a join key for causality.

The registry declares each identity's `status` and `trust_eligible` flag, and
`assert_producible()` refuses to emit a retired one. The invalidation contract
and the dirty marker both read `active_identity()` rather than restating a
literal, so the trigger DDL and the application default cannot drift apart.

Enforcement is not left to Python. Migration
`202608231200_b25_p13_c8_identity_window_causality` adds `CHECK` constraints on
both `b24_dirty_events` and `bayesian_model_fits` restricting `model_type` to
the registered set, so an unregistered identity cannot be stored by any writer
through any path.

`SUPPORTED_CONFIDENCE_MODEL_TYPES` in the Trust read model deliberately remains
a literal. Importing the Bayesian registry from the Trust path would breach the
B2.5-P12 isolation boundary, which forbids `app.bayesian` beneath
`app.api.trust_api`. The literal is instead bound to the registry by a static
gate, so the two are proven equal without being physically coupled.

### F-02 / F-03 — window dependency by overlap, on family identity alone

Staleness now asks the question it always meant to ask: *did anything change
inside the window this fit covers?*

```sql
AND dirty.model_type = requested_fit.model_type
AND public.b24_source_windows_overlap(
        dirty.source_window_start,  dirty.source_window_end,
        requested_fit.source_window_start, requested_fit.source_window_end)
```

`b24_source_windows_overlap` is half-open and immutable:
`p_change_start < p_fit_end AND p_fit_start < p_change_end`. A change at exactly
a fit's end boundary does not stale it; a change one microsecond earlier does.
`idx_b24_dirty_events_staleness_overlap` supports the predicate.

The `model_version` join is gone. A fit's producing pipeline version has no
bearing on whether the financial facts underneath it moved.

### F-04 — one authority renders both artefacts

`backend/app/bayesian/source_contract_authority.py` holds one structured
contract per governed relation — projection, membership, window key — and
renders **both** the canonical snapshot `SELECT` the application executes **and**
the invalidation trigger DDL the migration installs.

The gate no longer compares a string against its own `repr`. It reads the SQL
the database actually runs and compares it, whitespace-normalised, against what
the authority renders. Changing membership, projection or window key on either
side turns it red.

### F-05 — the change window and the fit window are different questions

`b24_dirty_events` records *when the source moved*. That is a change
description, and the day bucket is the right granularity for it — it is exactly
the precision F-02's overlap semantics depends on. It is the wrong description
of *what to fit*.

`fit_window_for()` in `app/bayesian/fit_planner.py` derives the fit window from
the change: it ends where the change window ends and reaches back at least
`SPARSE_PRIVACY_THRESHOLDS.minimum_source_window_density_days`. The bound is
**read from the contract that imposes it**, never restated, so the two cannot
drift. The widening is monotone — a caller that already supplied a window at
least that wide keeps exactly the window it asked for — which is why every
existing 30-day and 31-day proof is untouched by the change.

Widening the *trigger's* window instead was considered and rejected: it would
have made a change on day D stale fits that do not contain day D, undoing the
precision F-02 was remediated to obtain.

### F-06 — the authority is measured, not judged

`backend/app/bayesian/feature_cardinality.py` is the missing writer, and what it
is *not* is the design.

It computes **cardinality, not confidence**: the four widths the authority
schema already stores — `channel_count`, `currency_count`, `provider_count`,
`campaign_or_feature_count` — for one exact source snapshot. It contains no
threshold, consults no eligibility verdict, and reads every rule it applies from
an authority that already existed:

| Concern | Read from | Not invented here |
|---------|-----------|-------------------|
| Which rows are members | `SOURCE_CONTRACT_AUTHORITY.member_predicate()` | the same method that renders the invalidation trigger's predicate |
| What the caps are | `B24_RESOURCE_POLICY` | no number appears in the producer |
| How to count | `true_next_key_early_stop_cap_plus_one_v1` | the discipline B2.4 already adjudicated |
| Channel and currency width | the P2 preflight that already computes them | a second definition would be free to disagree with the one eligibility was decided from |

Only `provider` and `campaign_or_feature` needed new derivations, because P2
selects those columns but never aggregates them. Both use the same bounded walk
P2 already uses for channels — a loose index scan that visits one row per
distinct key and stops at `cap + 1`.

That stopping rule is the point of the counting discipline, and the producer
records it honestly. Twenty providers against a cap of sixteen are reported as
**seventeen**, not twenty, with `overflowed` recorded alongside. Seventeen says
exactly what the resource policy needs — *more than the cap* — and says nothing
it does not. Counting the remaining providers would be work performed to produce
a number that is discarded on arrival.

**Membership was unified rather than copied.** `SOURCE_CONTRACT_AUTHORITY` had
been restating the lifecycle inclusion values as literals; they agreed with
`LIFECYCLE_INCLUSION_RULES` only because someone kept them agreeing. That is the
F-01 defect in a different field, and deriving the producer from a contract that
could silently drift would have inherited it. The contract now reads those
values, so the producer, the canonical snapshot `SELECT`, the invalidation
trigger DDL and the eligibility preflight all resolve membership to one source.

**Freshness is snapshot identity, not elapsed time.** The producer recomputes
the source hash inside one repeatable-read transaction and writes only when the
hash it observes is the hash the request named. If the source moved, nothing is
written and the request parks exactly as before — which is correct, because the
bytes that request described no longer exist. This is strictly stronger than a
TTL: a one-second-old authority for a changed snapshot is already wrong, and a
year-old authority for an unchanged snapshot is still right. `computed_at`
remains provenance, never the freshness authority.

One incidental defect surfaced and was fixed on the way: `build_feature_authority`
receives its window as ISO text from the broker, and every existing consumer
bound it through psycopg2, which coerces silently. The producer binds through
asyncpg, which does not — so the boundary is now normalized explicitly rather
than by a driver's good manners.

## 5. C8-N — the contiguous journey, closed

The directive names this the principal closure gate. It is the only proof here
that could have discovered F-05 or F-06 — it discovered both — and it is now the
proof that they are closed.

One real financial fact changes, and every intermediate authority is produced by
the component that owns it:

```
a provisional verdict batch is confirmed        (ordinary UPDATE, app role)
  -> production invalidation trigger             writes the dirty evidence
    -> production wake-up trigger                makes the tenant due
      -> real celery beat                        emits onto a real broker
        -> real celery worker -Q bayesian        consumes it
          -> production planner                  derives a fittable window
            -> production cardinality producer   measures the snapshot's width
              -> production planner              creates the fit
                -> production confidence read    projects that fit
                  -> production Trust route      signs an envelope over it
                    -> published JWKS            verifies the signature
```

Nothing in that list is seeded by the test. There is no `append_dirty_event`
call, no hand-written `bayesian_model_fits` row, no hand-written feature
authority, no `.run()` standing in for delivery, and no dependency override
standing in for authentication. The credential is a real
`agent_service_credentials` row with a real scope grant, so the production
`authenticate_machine_caller` runs against it — scope check and replay check
included. The signing key is real Ed25519 material and the JWKS the envelope is
verified against is the document that signer publishes.

**The subject the envelope describes is a fit id the planner chose. The test
never picked it.** That single fact is what the audits said no proof in the
repository could establish.

The journey asserts at every seam against an artefact only that seam can
produce, so a break fails at the stage that broke rather than silently
shortening the chain:

| Stage | Asserted from |
|-------|---------------|
| invalidation | a `b24_dirty_events` row at the canonical identity, written by the trigger |
| wake-up | a `b24_fit_planner_wakeups` row, written by the trigger |
| Beat | the scheduler's own log naming the planner entry |
| broker | rows on the `bayesian` queue after a captured baseline |
| worker | a probe written from inside the task body, under the `app_worker` login |
| planner | an authority build request whose window is the **derived** one, not the trigger's day bucket |
| producer | a `fresh` authority whose snapshot hash is the hash the planner asked about |
| fit | one fit, carrying the identity the trigger emitted |
| Trust | a 200 from the production route with production dependencies |
| JWKS | `verify_trust_envelope` against a registry rebuilt from the public document |

It carries a negative interval throughout: before the worker starts, messages
are on the broker, the durable obligation is unmoved, and **no fit exists**. A
fit that could appear without a worker would mean the journey was proving
something about its own process.

And it closes with a correspondence check, which is the assertion that keeps the
rest honest. The envelope is signed and verifiable — that is not the same as
true. A planner-created fit has not been sampled, so the governed answer is a
withheld confidence rather than a number, and the envelope has to say so. An
envelope reporting a usable confidence for an unsampled fit would be a
*verifiable lie*, which is worse than an unverifiable one.

### What the frontier assertions became

While F-06 was open, C8-N asserted that the chain stopped at the missing
producer, and its failure message said what finding a producer would mean: that
the frontier had moved and the journey had to be extended. That is what
happened, and the two-sided pin was replaced rather than deleted.
`test_c8_the_feature_authority_producer_is_wired_and_derives_its_rules` now
requires that the producer exists, that `build_feature_authority` calls it, and
— the part worth guarding — that the producer states no policy of its own:
membership derived, caps read, walk bounded, no threshold, no TTL. Docstrings
are stripped before anything is scanned, so prose can neither pass nor fail a
check.

### Two pieces of environment isolation, stated plainly

Both make the claim harder rather than easier, and neither touches a row of the
journey's own evidence:

- The dirty evidence and wake-up produced by *building* the fixture are
  discarded before the change is made. From that point, any dirty row, any
  wake-up, any authority and any fit can only have come from the change under
  test.
- Other tenants' wake-ups and the broker backlog are cleared before the baseline
  is taken. This is not tidiness — see F-07 in §7. The planner leases its whole
  batch up front and disposes per tenant, so one unplannable residue tenant
  strands every tenant behind it for a ten-minute lease, and every obligation
  the planner *does* reach now costs a real snapshot read and a cardinality
  walk. In a database shared with the earlier proofs, this journey's own
  obligation can simply never be reached — which is starvation, not a broken
  chain, and would make the journey report the wrong finding. The same isolation
  was added to the C8 transport proof for the same reason, after the full
  rehearsal caught it starving.

## 7. What is proven, and what is not

Proven, end to end, with no substituted authority at any seam:

- **A real financial source change reaches a JWKS-verifiable Trust claim.** One
  ordinary `UPDATE` confirming a batch of provisional verdicts travels the
  production invalidation trigger, the production wake-up trigger, a real Beat,
  a real PostgreSQL broker, a real `celery worker -Q bayesian`, the production
  planner, the production cardinality producer, the production confidence
  projection and the production Trust route, and the resulting envelope verifies
  against the JWKS that route publishes. This is the directive's principal
  closure gate, and it is green.
- Window dependency is causal and precise in both directions: a change inside a
  fit's window stales it whatever the window's shape, and a change outside it
  does not.
- An unregistered or retired model identity cannot be stored, enforced by the
  database rather than by convention.
- Source membership resolves to one authority — the same values render the
  canonical snapshot `SELECT`, the invalidation trigger DDL, the eligibility
  preflight and the cardinality producer.
- The feature authority is measured rather than judged, is bounded by the
  adjudicated cap-plus-one policy, and is never written for a snapshot the
  producer did not itself observe.
- The signed claim corresponds to the pipeline's real state: an unsampled fit is
  reported as withholding confidence, not as carrying it.

Not claimed, and stated plainly:

- **Real PyMC sampling is not composed into this journey.** The journey's
  terminal claim describes a fit the planner created and that has not been
  sampled, which is why the correspondence check requires the envelope to
  withhold a confidence value. Posterior sampling is exercised by the B2.4-P6
  real-fit proof in its own workflow with the Bayesian dependency set installed.
  That proof supplies its own feature authority — which is exactly how F-06
  stayed hidden for as long as it did, and is worth remembering when reading any
  proof that begins from state it wrote itself.
- **F-05b, observed, no longer load-bearing.** The C5 dispatch fence rejects the
  planner's own governed fallback upsert — `b24_dispatch_fence_rejected` on a
  write the fence's own comment says the planner owns. F-05's remediation means
  the eligible path no longer reaches it, so nothing here depends on it, but the
  exemption is incomplete and is recorded rather than silently widened.
- **F-07, observed while building C8-N, not remediated.**
  `plan_due_fit_intents` leases its entire tenant batch up front through
  `b24_due_fit_planner_tenants`, then disposes each tenant in a per-tenant
  `finally`. An exception raised while planning one tenant propagates out of the
  loop, so every tenant leased *behind* the failing one is never processed and
  never disposed — it stays `leased` until its 600-second lease expires. One
  unplannable tenant can stall an entire deployment's planning for ten minutes at
  a time, and raising the batch size widens the blast radius rather than
  improving throughput.

  This was observed directly: with the batch raised to the task's ceiling, all
  six due wake-ups in a shared database were stranded under a single lease
  expiring ten minutes later, with the planner reporting `tenant_count=0` on
  every subsequent pass. C7 made wake-up *disposal* derive from residual
  authority rather than from Python control flow; the batch's failure semantics
  were not in its scope and remain a control-flow artefact.

  Neither C8-N nor the transport proof works around this by weakening an
  assertion. Both clear other tenants' wake-ups before they begin — each runs in
  a purpose-built database and neither touches a row of its own evidence — so a
  stranded batch cannot be mistaken for a chain that failed to conduct.

## 8. Verdict

**B2.5-P13 Corrective Action VIII: F-01 through F-06 are closed and proven.
F-05b and F-07 are recorded, observed, and carry no completion claim.**

The directive asked for a contiguous journey from a financial fact to a signed
claim. That journey now completes, and the two findings that stood in its way
were both discovered by building it rather than by inspecting the code.

That is the durable result here, and it is worth naming precisely. Every
individual proof in this system was green before this work, and the pipeline
could not conduct. The reason was not that any proof was wrong; it was that
every proof began from state it had written itself, so no proof could observe
the seams between them. Two independent audits found the first seam. The journey
found the second and the third — including a task that was registered, routed,
dispatched, retried, returned cleanly, and built nothing.

A proof that starts where the last one ended is the only kind that can find
that.
