## 4. H-XV-01 — Issuance capability was forgeable (Exit Gate A)

### The falsifier, and its result before remediation

Each attack authored its **own** payload carrying `verified_revenue_minor`
values no tenant earned, never ran the builder, and never wrote an audit row:

```text
[*** CAPABILITY ACQUIRED ***] A1 direct constructor + imported _CAPABILITY_SEAL :: verified_revenue_minor=999999999
[*** CAPABILITY ACQUIRED ***] A2 object.__new__ + object.__setattr__            :: verified_revenue_minor=888888888
[*** CAPABILITY ACQUIRED ***] A3 seal transplant via getattr from a donor       :: verified_revenue_minor=777777777
[refused]                     A4 raw caller dict to signer :: issuance_capability_required

CAPABILITY ACQUISITIONS OUTSIDE THE MINT PATH: 3
```

A1–A3 each produced a real Ed25519 signature that **passed
`verify_trust_envelope`**. This trips four of the directive's §15 automatic
failure conditions simultaneously.

### Established root cause

`AuthorizedTrustEnvelope` carried `_payload_snapshot` and validated it against
`authority_proof_hash`. That hash is a pure function of the payload **the holder
supplied**, and `_authority_proof_hash` was importable. So the "proof" proved
self-consistency, never provenance. The `_seal` check was not a boundary either:
`_CAPABILITY_SEAL` was a module global, and `getattr(donor, "_seal")` retrieved
it from any instance. The same design was present one layer earlier on
`TrustEnvelopeBuildWitness` via `_BUILD_WITNESS_SEAL`.

### Remediation

Two physical properties replace the naming convention
(`backend/app/trust/issuance_authority_ledger.py`):

1. **The authoritative bytes never travel with the handle.** Minting stores the
   canonical payload in a table held in a **closure cell**; the handle is a
   256-bit random string; redemption returns the *stored* bytes. The signer
   therefore reads the claim from the mint record, not from the object it was
   handed — so a fabricated or transplanted handle has no payload to smuggle,
   because the object carries none.
2. **Mint and redeem check the calling module** against a declared TCB
   (`app.trust.builder`, `app.trust.semantic_authority`, `app.trust.signing`).
   The check reads the *direct* caller, which stays the trust module itself even
   when work is hopped onto a worker thread by `asyncio.to_thread`.

Redemption is single-use, which also gives issuance a physical anti-replay
property.

### Result after remediation

```text
[refused] A1 direct constructor + fabricated handle       :: semantic_authority_refused:issuance_capability_invalid
[refused] A2 object.__new__ + object.__setattr__          :: semantic_authority_refused:issuance_capability_invalid
[refused] A3 direct ledger mint from outside the TCB      :: issuance_authority_untrusted_caller:mint:capability:__main__
[refused] A5 forged P5 build witness                      :: builder_authority_witness_invalid
[refused] A6 direct witness-ledger mint from outside TCB  :: issuance_authority_untrusted_caller:mint:witness:__main__
[refused] A4 raw caller dict to signer                    :: issuance_capability_required

CAPABILITY ACQUISITIONS OUTSIDE THE MINT PATH: 0
```

### Threat model — stated, not overclaimed

`docs/security/b25_p13_c15_trusted_computing_base.md` declares what this defends
against (every production-reachable caller outside the three trusted modules,
including all fourteen vectors the directive enumerates) and, explicitly, what
it does **not**: code that walks interpreter internals —
`function.__closure__[i].cell_contents`, `gc.get_objects()`, frame manipulation,
`ctypes`. That exclusion is honest rather than convenient: such code can read the
Ed25519 private key straight out of `TrustKeyRegistry` and sign anything, so no
capability design expressible in CPython can defend against it. Per the
directive's instruction, Python underscore and module privacy are **not**
described here as a security boundary — they are documentation, and the ledger
is the enforcement.

## 5. H-XV-02 / H-XV-03 — Audit-to-cryptographic-issuance truth (Exit Gate B)

### The failure-injection matrix

Executed against **live PostgreSQL 15.19** through a **real authenticated HTTP
journey** (`POST /api/trust/v1/envelopes/query`, production dependencies, no
overrides), forcing failure after durable P7 commit.

Before remediation:

```json
{"control_status": 200,
 "p8_fail_raised": "RuntimeError: XV_INJECTED_P8_PRIVATE_KEY_FAILURE",
 "issuance_success_rows": 2,
 "signed_envelopes_actually_delivered": 1}
```

Both rows read `event_type='issuance', status='success'` and **both carried an
`envelope_hash`**. Durable history asserted a completed issuance for a request
whose signature never physically existed — the directive's §15 condition *"P8
failure leaves durable state claiming completed issuance"*.

### Established root cause

`record_trust_audit_event_durable` commits the issuance row in an independent
transaction **before** the capability is minted and long before P8 runs. The
schema offered exactly one terminal shape for an issuance
(`ck_trust_access_log_status` allows only `success|refused|degraded|replayed`),
so authorization and completed issuance were the same durable fact, and the
vocabulary read as the stronger one.

### Remediation — and why `status` was deliberately left alone

`status` feeds `_audit_material`, whose `compute_audit_hash` produces
`audit_hash`, which is **bound into the signed envelope**. Changing it would
silently reinterpret every envelope already issued. It is preserved
byte-for-byte.

Migration `202608291200` adds `issuance_state` as the *physical* fact:

```text
authorized  -> P5/P7 passed; a capability may be minted
issued      -> a signature physically exists
failed      -> authorised, then abandoned without a signature
```

with the law expressed as database physics rather than application discipline:

```sql
CONSTRAINT ck_trust_access_log_issued_requires_crypto CHECK (
    issuance_state <> 'issued'
    OR (issued_at IS NOT NULL
        AND issued_signing_key_id IS NOT NULL
        AND issued_signature_hash ~ '^sha256:[0-9a-f]{64}$'
        AND envelope_hash IS NOT NULL))
```

plus the symmetric `ck_trust_access_log_unissued_has_no_crypto`. A future code
path that forgets to finalise **cannot** fabricate a completed-issuance row.

### Result after remediation

```json
{"rows_by_issuance_state": {"issued": 1, "failed": 2},
 "rows_claiming_completed_issuance": 1,
 "signed_envelopes_actually_delivered": 1}
```

`AUDIT HISTORY = PHYSICAL EVENT HISTORY` holds. The `issued` row carries
`issued_signing_key_id` and `issued_signature_hash`; the `failed` rows carry
neither.

### Retry and idempotency lineage

`test_c15_retry_after_failure_yields_one_coherent_lineage` fails the signer,
observes `issuance_state='failed'`, then retries **the same logical request**
and observes exactly one row, now `issued`, with the same `audit_ref`:
`c15_retry_lineage_rows=1`. `failed -> issued` is permitted (a retry may
complete what failed); `issued` is terminal, so a later failure cannot un-issue
real history.

The wall clock is pinned in that test for a substantive reason: `created_at` is
part of the audited material, so two attempts a second apart are genuinely
different requests, and the system correctly refuses to conflate them under one
idempotency key (`TrustAuditError: idempotency_conflict`). That refusal is a
coherent, explainable outcome — it does not create ghost or duplicate issuance —
and pinning the clock tests the intended physics rather than clock luck.

## 6. H-XV-07 — `KeyError: 'envelopes'` forensic disposition (Exit Gate C)

### What the XIV ledger recorded

> Exact technical-main push workflow `B2.5-P11 Export Compatibility` first failed
> in the maximum-resource evidence step with `KeyError: 'envelopes'`; its retry
> result is success on the same exact SHA.

Root cause was not established. Per §5 of the directive, a retry is not an
explanation.

### Reproduction

The failure was reproduced deterministically by narrowing the declared handler
deadline — driving the production route down its **contract-correct** refusal
branch, exactly as a slow hosted runner would:

```text
XV_EXPORT_RESPONSE={"status_code": 503,
                    "body": {"reason_code": "export_handler_deadline_exceeded",
                             "status": "refused"},
                    "body_keys": ["reason_code", "status"]}
E   KeyError: 'envelopes'
backend/tests/trust/test_b25_p11_postgres_physics.py:727: KeyError
```

Identical error, identical line.

### Causal chain

1. The handler exceeds `EXPORT_HANDLER_DEADLINE_SECONDS` (1.5 s).
2. `asyncio.timeout` fires; the route returns **HTTP 503**
   `{"status":"refused","reason_code":"export_handler_deadline_exceeded"}` — a
   body with no `envelopes` key. This is correct behaviour.
3. The test built `artifacts = [r.json() for r in responses]` and indexed
   `artifact["envelopes"]` at line 727.
4. Its own `assert all(response.status_code == 200 ...)` existed — **at line
   748, after the indexing.** The assertion that would have named the real cause
   ran too late to run at all.

### Classification: `CONFIRMED TEST DEFECT`

* The directive's **blocking falsifier is REFUTED.** No envelope data was lost
  or mis-associated; no cross-tenant contamination; the export composition never
  misbehaved. The key was absent because the response was a *refusal*.
* The directive's **proof-failure falsifier is CONFIRMED.** A `KeyError` is an
  illegible failure that makes a capacity event indistinguishable from a
  data-integrity defect, and retry-green then laundered it.

### The companion flake has the same address

XIV also recorded a P11 failure at **1518.735 ms against a 1500 ms assertion** —
the same test, the same deadline. That assertion compared a **client** wall-clock
measurement against a **server-side** handler deadline. Client latency
additionally carries ASGI transport, JSON serialization and event-loop
scheduling, so it is always ≥ the server figure and can fail while the server
honoured its contract perfectly. Measured local margin: **1161.92 ms against
1500 ms** — only ~28% headroom on an assertion measuring the wrong quantity.

### Remediation

1. The status and shape assertions move **ahead** of the indexing, so a deadline
   refusal fails as a legible capacity finding.
2. The load-bearing server contract is proven by the 200-vs-503 assertion
   (exceeding the deadline is precisely what produces 503). The client bound is
   retained but now names the transport overhead it actually measures
   (`CLIENT_TRANSPORT_OVERHEAD_BUDGET_MS`), sized from the measured margin rather
   than chosen to turn a red run green.

## 7. Local reproducibility and bootstrap portability (Exit Gates D, E)

### H-XV-09 — established root cause

The bootstrap script is **LF in git**. There was **no `.gitattributes` at all**,
so the repository declared no line-ending policy and what landed in a working
tree depended on each developer's Git config. Git for Windows ships
`core.autocrlf=true` in its **system** config:

```text
$ git config --system --get core.autocrlf
true
```

A fresh clone on a stock Windows host therefore rewrote every `.sh` to CRLF.
Verified by running the checkout filter and executing the result:

```text
$ git -c core.autocrlf=true cat-file --filters ":scripts/ci/run_m1_onboarding_bootstrap.sh" | head -3 | cat -A
#!/usr/bin/env bash^M$
set -euo pipefail^M$

$ docker run --rm bash:5.2 bash crlf_min.sh
crlf_min.sh: line 1: set: pipefail: invalid option name
EXIT=2
```

That reproduces the independent auditor's observation exactly. Per the
directive: **broken bootstrap = broken supported build path.**

### Remediation and proof

`.gitattributes` pins `eol=lf` for shell, `Makefile`, `Procfile`, `Dockerfile*`
and newline-sensitive formats, and `eol=crlf` for `*.ps1`/`*.bat`. After the fix,
under the same stock-Windows simulation:

```text
$ git -c core.autocrlf=true cat-file --filters ":scripts/ci/run_m1_onboarding_bootstrap.sh" | head -3 | cat -A
#!/usr/bin/env bash$
set -euo pipefail$

$ docker run --rm bash:5.2 bash -n gitattr_bootstrap_probe.sh ; echo $?
0
$ ... bash /tmp/t.sh
BOOTSTRAP_PREAMBLE_OK
```

and PowerShell keeps CRLF (`# Bootstrap Local PostgreSQL ...^M$`).

### H-XV-08 — supported-environment matrix

`docs/environment/SUPPORTED_ENVIRONMENTS.md` now states the support contract and,
critically, the **topology contracts** — which of the four surfaces satisfies
which invariants. The load-bearing statement:

> **The minimal local developer surface does not start the Bayesian worker or
> the publisher.** That is deliberate, not a gap. An auditor who expects the full
> production topology from `docker-compose.local.yml` will correctly find it
> absent, and that is the documented boundary rather than a defect.

That single sentence dissolves the disagreement between the two independent
audits: both observations were correct, and the repository had simply never said
which was the contract. Unsupported environments are now named explicitly so

### Infrastructure evidence capsules

`docs/environment/INFRASTRUCTURE_EVIDENCE_CAPSULES.md` records three capsules
(`IEC-XV-01` PostgreSQL/role/migration topology, `IEC-XV-02` Compose surfaces,

**The rule was exercised, not merely written.** `IEC-XV-01` was *invalidated* by

## 8. H-XV-10 — Historical end-user serviceability (Exit Gate F)

### Determining the governed contract first

The repository exposes exactly five Trust HTTP routes. There is **no
server-side historical-retrieval endpoint and no signed-envelope persistence**,
by design: the envelope *is* the artifact and the holder keeps it. The governed
historical contract is therefore **bearer-of-artifact verification** through
`POST /trust/v1/verify` against historical key authority published as
public-only JWKS.

Per the directive's instruction not to implement speculative remediation, no
retrieval subsystem was invented. The contract that exists was proven end to end,
and the boundary is documented so nothing implies a retrieval API that does not
exist.

### The executed journey

`test_c15_historical_envelope_serviceable_over_http_after_key_rotation`, against
live PostgreSQL over the real authenticated HTTP boundary:

```json
["issued_under_generation_n", "rotated_to_generation_n_plus_1",
 "application_rebuilt", "historical_kid_publicly_resolvable",
 "historical_semantics_preserved", "no_substitute_reissue",
 "no_recompute_on_retrieval", "cross_tenant_refused"]
```

Each catastrophic falsifier from directive §6 H-XV-10 is addressed:
