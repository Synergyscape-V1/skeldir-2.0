## Hypothesis Ledger

H-P4-01 - No authoritative money source registry exists
Status: CONFIRMED
Evidence: No prior `money_authority_registry.py` existed, and current B2.5 contract money fields had no total registry mapping.
Root cause: P1-P3 intentionally stopped before money source authority.
Remediation: Added `backend/app/trust/money_authority_registry.py` with explicit TrustEnvelope field policy and approved source mappings.
Post-remediation proof: Validator checks every discovered TrustEnvelope money field has a registry entry and at least one approved source.
Residual risk: Future TrustEnvelope money fields must update the registry and P4 validator.

H-P4-02 - Legacy dashboard/export/budget floats can still be mistaken for authority
Status: CONFIRMED
Evidence: Legacy float fields remain in attribution, revenue, export, and budget surfaces.
Root cause: Those DTOs are display/API compatibility surfaces, not TrustEnvelope authority sources.
Remediation: Adapter refuses forbidden DTO domains and field names with `money_source_not_authoritative`.
Post-remediation proof: Unit tests and validator include DTO/export/budget float rejection controls.
Residual risk: Later builder work must call the adapter rather than reading DTO fields directly.

H-P4-03 - Float-only legacy states may crash future TrustEnvelope issuance
Status: CONFIRMED
Evidence: Legacy floats are present and could otherwise be the only available value.
Root cause: No typed degraded/refused money-authority decision existed for float-only inputs.
Remediation: Adapter returns typed refusal/degraded decisions instead of throwing or rounding floats into authority.
Post-remediation proof: Tests cover legacy float-only refusal and missing mapped source degradation.
Residual risk: Future builder integration must preserve typed decisions.

H-P4-04 - Decimal strings may be converted through binary float
Status: CONFIRMED
Evidence: Existing generic money helpers are not P4-specific and do not prove TrustEnvelope source authority by string-only Decimal conversion.
Root cause: Provider decimal strings need exact conversion under source and currency policy.
Remediation: Adapter accepts provider decimal strings only as strings, rejects floats/Decimal objects, and parses with `Decimal` from string only.
Post-remediation proof: Tests and validator cover USD/EUR/JPY/KWD conversion, scientific notation rejection, currency-symbol rejection, and Decimal-object rejection.
Residual risk: Supported currency set is intentionally explicit.

H-P4-05 - Currency exponent handling may be incomplete or wrong
Status: CONFIRMED
Evidence: Existing generic helper behavior assumes common two-decimal money semantics.
Root cause: TrustEnvelope money authority needs explicit exponent policy and fail-closed unknowns.
Remediation: Registry declares explicit exponents for USD, EUR, GBP, CAD, AUD, JPY, and KWD, and the adapter rejects cents-labeled source mappings for non-2-exponent currencies.
Post-remediation proof: Tests and validator prove JPY zero-decimal, KWD three-decimal, USD sub-minor rejection, unknown currency rejection, and JPY/KWD rejection for `verified_total_cents`.
Residual risk: Additional currencies require explicit registry changes and validator coverage.

H-P4-06 - Negative and zero money semantics may be ambiguous
Status: CONFIRMED
Evidence: `verified_revenue_minor` semantics allow zero but not negative values; no P4 field policy existed.
Root cause: Global money rules are unsafe across revenue/refund/adjustment semantics.
Remediation: Registry uses field-specific `MoneyFieldPolicy`.
Post-remediation proof: Tests and validator prove zero accepted and negative rejected for `verified_revenue_minor`.
Residual risk: Refund/adjustment fields must add explicit field policy before use.

H-P4-07 - Authoritative money may bypass P2 numeric rejection
Status: REFUTED
Evidence: P4 introduces a new adapter path, so it must prove it emits only integer minor units and preserves P2.
Root cause: Without explicit tests, raw floats/Decimal ambiguity could reach canonical trust payloads.
Remediation: Adapter returns integer `minor_units` only for accepted authority and refuses/invalidates floats.
Post-remediation proof: P2 validator is chained inside the P4 validator and P4 tests reject raw floats.
Residual risk: Future builder work must consume the adapter rather than constructing money payloads directly.

H-P4-08 - P4 may accidentally implement builder behavior
Status: REFUTED BY SCOPE GUARD
Evidence: P4 changes are limited to registry, adapter, tests, CI validator, workflow, governance docs, and evidence.
Root cause: B2.5 later-phase surfaces are tempting but explicitly out of P4 scope.
Remediation: Validator scans for route/builder/signing/auth/audit/export/MCP/action overreach tokens in P4 files.
Post-remediation proof: Scope-overreach controls are part of the P4 validator marker set.
Residual risk: Later phases must add their own gates when those surfaces become authorized.

H-P4-09 - Money authority result shape may not be contract-ready
Status: CONFIRMED
Evidence: No typed result shape existed for accepted/refused/degraded/invalid money authority decisions.
Root cause: Bare booleans or ambiguous `None` would be insufficient for future TrustEnvelope issuance.
Remediation: Added typed dataclasses for accepted, refused, degraded, and invalid decisions with source/conversion/reason metadata.
Post-remediation proof: Unit tests and validator assert typed result shape and reason codes.
Residual risk: Future builder contract must map these typed decisions explicitly.

H-P4-10 - P4 CI may be marker theater
Status: REFUTED
Evidence: A new P4 validator is required to include positive, negative, and meta-negative controls.
Root cause: Marker-only scripts can go green without proving failure modes.
Remediation: Validator includes registry totality, DTO float rejection, exponent, sub-minor, unknown currency, negative/zero policy, P1/P2/P3 regression, scope, and meta-negative controls.
Post-remediation proof: Local full validator emitted all required nonzero markers, including `meta_negative_controls_passed=7`; PR and main B2.5-P4 workflow runs passed.
Residual risk: Later phases need their own non-vacuity controls when they expand beyond P4.
