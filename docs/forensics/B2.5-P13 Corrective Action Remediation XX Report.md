### Why the HMAC tenant-context redesign was rejected

The inherited migration stored a deployment HMAC key in a runtime-inaccessible table and rewrote every `public` tenant policy from `current_setting('app.current_tenant_id')` to a `SECURITY DEFINER` verifier, so a holder of the shared runtime credential could not select its own tenant. - the repository has **1,392 occurrences of `app.current_tenant_id` across 202 files** — migrations, tests, CI workflows, ops scripts. Every one of them is a call site the redesign changes the meaning of, under 75 required contexts;

- H-XX2-02 defines a sibling overgrant as *"process A can manufacture process B's load-bearing premise."* A different **tenant** is not a different **process**; the API's tenant scoping is the API's own premise, derived from server-side auth. It is not another process's.

The work is preserved in a git stash (`xx2: inherited HMAC tenant-context redesign (out of Corrective XX scope, archived)`) and recorded in the debt register below, not discarded silently.

## 4. Verdict-grant root cause and repair

Two heads, which is why a single grant edit would not have held:

1. `202604291200_b23_p1_schema_authority_lock.py:363` — direct grant to `app_user`;
2. same migration `:367` — grant to `app_rw`, which `app_user` inherits;
3. `202605061200_b23_p4_queue_performance_indexes.py:110` — **re-granted** the direct privilege after an earlier revoke in the same lineage.

Point 3 is the empirical reason the repair does not rely on grants alone. Authority is now expressed twice:

- **privilege** — `b23_match_verdicts` revoked from `PUBLIC`, `app_user`, `app_rw`, `app_ro`; `SELECT` back to `app_user`/`app_ro`; `SELECT, INSERT, UPDATE` to `app_worker`;
- **consequence** — `trg_b23_verdict_authorship_insert` / `_update` call `b23_enforce_verdict_authorship()`, which refuses unless the `session_user` is a superuser, holds the relation owner's role, or holds `app_worker`.

The trigger fires on INSERT, and on UPDATE only when a column that *is* verdict truth changes (13 columns: status, the four transition timestamps, match quality, and the six money/discrepancy columns). `attribution_events` and `webhook_ingress_identities` reference the table `ON DELETE SET NULL`; that referential action is a governed consequence of deleting the referenced row, not an assertion of verdict truth, and §5 proves it still works.

`session_user` rather than `current_user` is deliberate: `SET ROLE` changes `current_user` only, and `app_user` cannot `SET ROLE app_worker` in any case (§5, probe 6).

## 12b. Open-world hypotheses (Gate W)

Derived from this session's own investigation, not supplied by the directive. None is a replay of a known historical defect.

- **H-XX2-N01 — the migration principal is a universal verdict author.** `migration_owner` is a member of both `app_user` and `app_worker` (PostgreSQL requires membership to transfer object ownership, and the planner's `SECURITY DEFINER` functions must be owned by `app_worker`). Anything holding the migration DSN can therefore author verdict truth through both layers of the C20 fence. The only thing standing between a leaked migration credential and verdict authorship is the C7 topology gate's assertion that the migration DSN is never issued to an API or worker process. That assertion was not re-exercised here. `UNRESOLVED — NON-BLOCKING` (it is the documented, governed exception, not a new hole).
- **H-XX2-N02 — ownership is the trigger layer's escape hatch.** The guard admits the relation's owner. An ownership transfer of `b23_match_verdicts` to a runtime role, or a membership grant into the migration role, would open the trigger layer silently and leave only the privilege layer. **Closed in this corrective**: `test_c20_no_runtime_principal_inherits_the_relation_owner` asserts no production login can act as the owner.
- **H-XX2-N03 — allocation membership is still API-authored.** `app_user` retains `SELECT, INSERT, UPDATE, DELETE` on `attribution_allocations`, because the attribution recompute worker legitimately runs under it. `verified` / `verification_source` are trigger-derived and re-derived (audit 63 proved the caller value is discarded), but *which channels an event has an allocation for* is authored by the API principal, and B2.4 source membership reads that set. Whether a rogue API path could move a B2.4 decision by rewriting allocation rows without touching `verified` is unexamined. `UNRESOLVED`.
- **H-XX2-N04 — invalidation is a resource surface, not a truth surface.** `app_user` holds `SELECT, INSERT, UPDATE` on `b24_dirty_events` and `b24_feature_authority_build_requests`. Those are pull signals rather than truth, but a principal that can mark arbitrary windows dirty can force unbounded B2.4 replanning. Not a fabrication primitive; a cost primitive. `UNRESOLVED — NON-BLOCKING`.
- **H-XX2-N05 — a timeout is not an admission, but it is pressure.** The merge queue's `check_response_timeout_minutes` is 60 while R7 has historically run 24–76 minutes. A timed-out merge group refuses the candidate, so no unproven code lands — but repeated timeouts create exactly the operational pressure to shrink the required set that produced the historical gap. The §8.5 alignment reduces R7's runtime variance; the timeout itself was left at 60 by explicit decision and is in the debt register.
