## 3. Required physical state-machine matrix (directive §18)

### 3.1 Enumeration of legitimate post-terminal fit mutations

Before designing anything, every production writer of `bayesian_model_fits` was enumerated:

| Writer | Gate on the UPDATE |
|---|---|
| `fit_execution.py` `_mark_fit_fallback` | `status IN ('pending','queued','running','persist_pending')` |
| `fit_execution.py` `_mark_fit_diagnostic_error` | same |
| `fit_execution.py` storage-quota failure | same |
| `fit_execution.py` `sampled_unvalidated` | same |
| `fit_execution.py` success terminalisation | same |
| `fit_execution.py` `running` transition | `status IN ('pending','queued','running')` |
| `runtime_state.py` `mark_fit_timeout` / `_sync` | `status IN ('queued','running')` |
| `runtime_state.py` `sweep_stale_running_fits` | `status = 'running'` |
| `e2e_harness.py` success / running | same as the corresponding production paths |
| `b24_ack_recoverable_dispatch_failure` (SQL) | `status IN ('pending','queued','running','persist_pending')` |

**Result: there are zero legitimate post-terminal mutations of `bayesian_model_fits` in production.** A database-level terminal freeze is therefore compatible with every legitimate lifecycle and recovery path — it forbids nothing any writer actually does.

### 3.2 The resulting two-rule physics

| Status class | Members |
|---|---|
| Non-terminal (mutable) | `pending`, `queued`, `running`, `persist_pending`, `sampled_unvalidated`, `diagnostics_pending` |
| Terminal (frozen) | `succeeded`, `failed`, `timeout`, `worker_lost`, `fallback_only`, `cancelled` |

**Rule A — authority fence (`b24_enforce_dispatch_fence`, re-scoped).**
Changing an authority-bearing column requires a currently valid dispatch lease for that exact fit. Changing only inert bookkeeping does not.

**Rule B — terminal epistemic immutability (`trg_b24_terminal_fit_truth`, new).**
Once a fit is terminal, nothing it publishes may change again — lease or no lease.

The two rules deliberately cover **different** column sets, because they answer different questions. Rule A asks *may this caller change what the fit asserts*; Rule B asks *is this observation still open at all*, and a finished observation does not change in any respect. `TERMINAL_FROZEN_COLUMNS = LEASE_GATED_AUTHORITY_COLUMNS + ("updated_at",)`.

That one-column difference is load-bearing, and finding it is recorded here because the first draft of this remediation got it wrong. `updated_at` is not authority the planner needs a lease for on an open fit — but it is reachable from the signed wire. The read model computes `observed_at` as `completed_at or updated_at`; `completed_at` is **nullable even for available confidence** (no constraint requires it); and `observed_at` is published as five `provenance_chain[].observed_at` values that the hash manifest registers as machine authority and the signature commits to. Leaving `updated_at` outside Rule B would have let a tenant-scoped writer holding no dispatch lease shift signed provenance timestamps on a finished fit — a smaller lie than rewriting a confidence bucket, but the same kind of lie. It stays outside Rule A because gating it there would re-break the claim path the corrective exists to repair.

**Rule C — absolute temporal plausibility (`trg_b24_evidence_temporal_plausibility`, new).**
`source_read_started_at`, `source_read_completed_at` and `confidence_classified_at` may not exceed `now() + b24_evidence_future_skew_tolerance_seconds()`.

Composition: an authority change requires *both* a non-terminal row *and* a valid lease. Rule B is what closes the exploit, and it does so **without depending on lease acquisition being unforgeable** — which matters, because §3.3 shows it is not.

The **lease-gated authority column set** (Rule A), which Rule B freezes along with `updated_at`: `status`, `source_snapshot_hash`, `source_read_started_at`, `source_read_completed_at`, `data_completeness_status`, `fallback_applied`, `fallback_reason`, `diagnostic_status`, `diagnostic_failure_reason`, `diagnostic_policy_version`, `diagnostic_target_filter_version`, `diagnostics_computed_at`, `credible_interval_status`, `interval_policy_version`, `interval_shape`, `interval_element_count`, `interval_summary_bytes`, `hdi_lower`, `hdi_upper`, `r_hat_max`, `ess_min`, `divergence_count`, `n_chains`, `n_samples_actual`, `runtime_seconds`, `sampling_started_at`, `last_fit_at`, `completed_at`, `artifact_ref`, `artifact_hash`, `confidence_bucket`, `confidence_bucket_reason`, `confidence_policy_version`, `confidence_semantics_version`, `confidence_classified_at`, `confidence_evidence_snapshot_hash`, `confidence_deterministic_revenue_minor`, `confidence_deterministic_row_count`, `confidence_match_verdict_count`, `confidence_currency_count`, `max_runtime_seconds`, `max_samples`, `max_cores`.

**Columns a caller may change without a dispatch lease, after C5, are exactly three:** `updated_at`, `eligibility_status`, `last_eligibility_check_at` — and on a *terminal* fit, only the latter two, because Rule B freezes `updated_at`.

`eligibility_status` and `last_eligibility_check_at` are not selected by the Trust projection SQL at all (verified by inspecting `_EXACT_FIT_PROJECTION_SQL` directly, not by reading the code that builds it) and neither bounds compute. `updated_at` *is* selected, which is why it is frozen once the fit is terminal; on an open fit its only path to the wire is `observed_at`, and an open fit cannot yield available confidence. The resource ceilings were added to the frozen set specifically so the relaxation could not be characterised as widening anything beyond inert bookkeeping.

### 3.3 Disclosed residual: how the lease was obtained

The exploit's reclaim step succeeds **and still succeeds after C5**, deliberately. `b24_fit_dispatch_outbox` carries `tenant_isolation_policy_b24_fit_dispatch_outbox`, a **permissive `ALL` policy keyed only on `tenant_id`**, so the ordinary runtime identity can rewrite its own lease bookkeeping (`assigned_worker_generation`, `assignment_expires_at`, `lease_expires_at`); `b24_register_worker_process_authority` is `EXECUTE`-granted to that identity; and `b24_claim_fit_dispatch` then legitimately returns `RECLAIMED`.

That path is left intact on purpose, for two reasons:

1. It is genuine B2.4-P9 recovery physics. Narrowing it inside a P13 corrective would be exactly the "fix P13 by weakening a B2.4 fence" the directive forbids.
2. Making terminal truth depend on that path being unforgeable would be the same category of mistake as the original defect. C5 instead makes the *final write* impossible regardless of how the lease was obtained — which the journey proves by acquiring a real reclaimed lease and then failing to write.

Recorded as a residual architectural observation for the phase owner, non-blocking for P13: the outbox's write authority is broader than its lease model implies. It no longer reaches any truth-bearing state.

## 5. Exit Gates C5-C and C5-D — Production claim operability and same-snapshot lifecycle

### 5.1 The semantic decision the directive required first (§8)

> Is `confidence_projection:<fit_uuid>` an immutable historical observation, or may the same fit UUID acquire a later observation timestamp because identical source content was seen again?

**Answer: immutable.** The fit's unique key is `(tenant, model_type, model_version, window_start, window_end, source_snapshot_hash)` — the UUID *names one observation of one exact source content*. Refreshing its evidence timestamps on re-observation would silently re-date evidence an already-issued, already-signed envelope asserts, breaking P2 semantic identity, audit reproducibility, and the meaning of `evidence_snapshot_at`. The pre-existing SQL already refused to re-queue a terminal fit; restating its `source_read_*`, `data_completeness_status` and `fallback_*` was the inconsistency, not a feature.

### 5.2 Remediation

* `next_recovery_at` supplied in the dispatch-outbox INSERT.
* Every authority assignment in the `ON CONFLICT DO UPDATE` wrapped in `CASE WHEN b24_fit_status_is_terminal(...) THEN <old> ELSE <new> END`, so a terminal row keeps its evidence verbatim and Rule B and this SQL cannot drift apart.
* Outcome projection now distinguishes reuse: a fresh INSERT is always `queued`, so a terminal status on the conflict path can only mean an already-finished observation → `FitClaimOutcome.REUSED`.
* The execution lane is closed rather than held for a reused terminal fit, so a finished run does not hold the one-active-execution lease for an hour with nothing executing.
* `succeeded` added to `claimable_execution_lane` (defect #6 in §1).

### 5.3 Required claim/reuse experiment matrix (directive §19)

Journey `P13-C5-02-production-claim-seam-operability` drives the **real** `claim_fit_for_snapshot()` — no hand-seeded fit rows — six times:

| stale execution lane | `claimed` | reclaimed | reclaimed | reclaimed | scheduled | as read |

## 7. Exit Gates C5-F, C5-G, C5-H — Temporal and freshness truth

### 7.1 The governed skew policy

`EVIDENCE_FUTURE_SKEW_TOLERANCE_SECONDS = 120` in `app/confidence_projection/policy.py`, mirrored by `public.b24_evidence_future_skew_tolerance_seconds()`. A bounded tolerance rather than a strict `<= now()` because the database clock and the API clock are genuinely different clocks. `NC-C5-05` proves the two cannot drift: changing the migration's constant by one second turns the gate red.

Enforcement is layered, each layer independent:

* **Producer:** `trg_b24_evidence_temporal_plausibility` refuses the write.
* **Consumer:** `persisted_confidence_decision` checks plausibility *first*, for every row — because rows written before the trigger existed are still readable, and the reader must not trust that the producer was always governed. New reason `evidence_timestamp_implausible`, which maps through the builder's existing `else` branch to the already-published `confidence_unavailable`, so no wire enum changed.
* **Builder:** `temporal_authority_available` now requires plausibility as well as ordering. The `max(0, …)` clamp can no longer convert a materially negative age into zero, because materially future evidence never reaches that branch.

### 7.2 Truthful freshness semantics

Two new fields on `evidence_temporal_boundary`, both registered load-bearing in `semantic_truth_v1`:

| Field | Values | Meaning |
|---|---|---|
| `data_freshness_bound` | `exact` \| `at_least_ceiling` \| `unavailable` | How to read `data_freshness_seconds`. `at_least_ceiling` says the true age exceeds the representable maximum, so the number is a **lower bound and not the age** |
| `evidence_age_status` | `within_supported_horizon` \| `beyond_supported_horizon` \| `unavailable` | Absolute age, **independent of lineage** |

`staleness_status` keeps its meaning and now states it in the contract: *"Lineage currency, NOT absolute freshness. `current` means no superseding source snapshot is known for this subject; it makes no claim about how old the evidence is."* This is the §12 option the directive explicitly permits — retain `current` for lineage, provided absolute age is separately and truthfully represented. `NC-C5-07` fires if that disclaimer is removed.

## 8. Exit Gate C5-I — Full G5 adversarial composition

Report 36 was right and the fix is larger than seeding two more strings, because the three declared classes land on **different cells of the P3 disposition matrix**:

| Class | Payload shape | Detected risk | Disposition | Wire trust class |
|---|---|---|---|---|
| 0 | natural-language instruction override | `safe_printable` | `emit_untrusted_display_label` | `untrusted_display_label` |
| 1 | JSON / tool-call shaped | `tool_call_syntax` | `omit_raw_text_and_emit_quarantine_metadata` | `quarantined_text_hash` |
| 2 | delimiter / HTML / script breakout | `markup_or_script` | `omit_raw_text_and_emit_quarantine_metadata` | `quarantined_text_hash` |

A single hard-coded expectation could only ever have been right for one of them — part of why the other two were never routed. The journey therefore derives the expectation by running the production projection over the exact payload and comparing the wire field by field.

Each class independently demonstrates all five required properties:

```

   "class1:raw_text_sha256_of_exact_source",

1. **Positive source witness** — the exact bytes are committed in the envelope, by escaped display form or by `raw_text_sha256` over the exact source. 2. **Deterministic disposition** — asserted against the production projection for that input, not against a constant.
3. **No authority-field contamination** — the pre-existing check, now earned by a witness rather than vacuous.
4. **Correct quarantine metadata** — `raw_text_sha256` compared to an independently computed `sha256:` of the payload.
5. **Valid final signature** — each envelope re-verified through the public-only JWKS registry.

## 9. Exit Gate C5-J — Behavioral proof non-vacuity

### 9.1 Classification (directive §14, §42)

All 33 C3/C4/C5 negative controls are classified in `CONTROL_CLASSIFICATIONS`, machine-checked, and printed by the gate. Completeness is enforced **in both directions**: a control id present in a source but missing from the registry fails, and vice versa.

```
p13_c5_controls_classified=34
p13_c5_behavioral_invariants=25
p13_c5_static_invariants=9
p13_c5_causal_controls=18
p13_c5_source_controls=16
p13_c5_behavioral_backstops=10

## 15A. Closure addendum — what the merge itself exposed

Landing this change surfaced three defects that had nothing to do with the trust
chain and everything to do with whether the proof system can be trusted. They are
recorded because a corrective that reports only its planned work is the kind of
record Report 36 was able to falsify.

**1. The P13 job's `MIGRATION_DATABASE_URL` named a role that does not exist.**
The workflow set `migration_user`; the shared `setup-postgres-ci` action
provisions `migration_owner`. The variable had been wrong since the job was
written and never failed, because nothing in the job read it until C5's
legacy-row seeding did. Corrected in `b618751c7`.

**2. A new CI enforcer must declare itself, in two places.**
`validate_b25_p13_c5_closure.py` had to be registered in
`docs/ci/enforcer_registry.yaml` and in `docs/ci/gate_subsumption_matrix.yaml`
with an explicit `keep_required` decision arguing why C3 and C4 do not subsume
it. M3 CI Governance blocks an unregistered enforcer, correctly.

**3. "Not a required context" does not mean "does not block".**
The `main-merge-queue` ruleset uses `grouping_strategy: ALLGREEN`, so the queue
requires *every* check in the merge group green — not only the 75 contexts
classic branch protection enumerates. `m1-local-dev-authority` is absent from
the required list and still dequeued this PR. This had not surfaced before
because the merge queue was enabled (PRs #653/#655, 2026-08-19) *after* the last
migration-bearing PR merged (#649, 2026-08-18), making this the first migration
to traverse it.

The fix was the repository's own established convention, which an earlier draft
of this document got wrong: `ALLOWED_M1_PATH_PREFIXES` already names every prior
phase migration, B2.4-P1 through B2.5-P13-C4. Both `M0` and `M1` scope-lock
allowlists are live maintained surfaces extended per phase, not frozen records.
Adding the three C5 artifacts to M1 also cleared its prohibited-path failure,
because that check reads `matches_prohibited AND NOT _allowed_m1_path(path)`.

**Standing guidance for the next migration-bearing phase:** extend
`ALLOWED_M0_PATHS` *and* `ALLOWED_M1_PATH_PREFIXES` with the migration, the new
validator and the evidence pack; register the validator in the enforcer registry
and the subsumption matrix; and verify mergeability against the merge queue's
ALLGREEN strategy rather than against the required-contexts list alone.
