## 0. What this corrective is, in one paragraph

Two independent audits looked at the same protected main. Audit 64 exercised the
whole trust journey end to end on its own greenfield nine-process topology and
found it honest: webhook → B2.3 verdict → DB-derived verified allocation → real
four-chain PyMC posterior → bounded confidence → read-only Trust projection →

verification, with signer-removal failing closed. Audit 65 reproduced the same
composition and agreed — and then asked a different question: *not* whether the
journey tells the truth, but whether any process can rewrite another process's
premise after the fact. It found two places where the API database principal
could. Corrective XXI closes exactly those two, plus the siblings the same
historical grants reached, and makes both defect classes mechanically
unmergeable. It changes nothing else.

Both defects are the same historical shape Corrective XX found on verdicts:
**authority derived from tables rather than from causal meaning** (directive
`RC-XXI-01`, `RC-XXI-02`, `RC-XXI-04`).

### `b24_dirty_events`

`alembic/versions/007_skeldir_foundation/202605221430_b24_p3_fit_planning_outbox.py:328`

```python
for table, policy in (
    ("b24_dirty_events", ...),
    ("b24_active_execution_leases", ...),
    ("b24_fit_dispatch_outbox", ...),

    _grant_if_role_exists("app_user", f"GRANT SELECT, INSERT, UPDATE ON public.{table} TO app_user")
```

it as freshness authority.

Physically observed at `202609021200`: `app_user` holds `INSERT, SELECT, UPDATE`
by **direct** grant; `app_rw` holds nothing on this relation, so this head is
single. No column-level grants narrow it.

## 5. The remediation

`alembic/versions/007_skeldir_foundation/202609031200_b25_p13_c21_freshness_and_issuance_authority.py`

Authority is expressed twice on each surface, for the reason Corrective XX
established empirically: `202605061200` re-granted a privilege an earlier
migration had revoked, so a privilege layer alone is one migration away from
regression.

### Layer 1 — privilege

| relation | `app_user` | `app_worker` | `app_rw` | `app_ro` | others |
|---|---|---|---|---|---|
| `b24_dirty_events` | `SELECT, INSERT` | `SELECT, INSERT, UPDATE` | — | `SELECT` | — |
| `trust_envelope_issuance_log` | `SELECT, INSERT` | `SELECT, INSERT` | `SELECT, INSERT` | `SELECT` | — |
| `trust_replay_events` | `SELECT, INSERT` | `SELECT, INSERT` | `SELECT, INSERT` | `SELECT` | — |
| `trust_scope_denial_events` | `SELECT, INSERT` | `SELECT, INSERT` | `SELECT, INSERT` | `SELECT` | — |
| `trust_access_log` | `SELECT, INSERT, UPDATE` | `SELECT, INSERT, UPDATE` | `SELECT, INSERT, UPDATE` | `SELECT` | `app_trust_issuer`, `app_trust_signer`: `SELECT, UPDATE` |

`UPDATE` is what the corrective is about, so `UPDATE` is what goes — from the
direct grant *and* the inherited one — on the issuance log and the two
INSERT-only sibling audit relations. `INSERT` stays, for the reason recorded in
the first-red ledger below: `record_trust_audit_event` writes all three from
whichever session composed the Trust read.

`trust_access_log` is left untouched. Its `UPDATE` is load-bearing —
`_upsert_access_log` increments a replay counter through `ON CONFLICT DO UPDATE`
— and the C16 guard `trust_access_log_issuance_authority_guard` already refuses
any change to an issuance-consequence column from a principal that is not the
issuer or the relation owner. It is nevertheless pinned in the authority
contract, so a future widening of the columns that guard does not cover still
has to pass through an equality assertion.

Neither C21 defect is reachable through any residual grant: the immutability
trigger refuses `UPDATE` and `DELETE` on the issuance log for every non-owner
principal, whatever privileges it holds.

### Layer 2 — consequence

`public.b24_enforce_dirty_event_authority()`, on
`BEFORE UPDATE ... FOR EACH ROW WHEN (<any evidence-identity column changes OR
source_snapshot_hash changes>)`:

1. superuser returns early — it can drop the trigger, so refusing it buys no
   authority and only breaks provisioning;
2. the relation owner returns early — same argument; C20 already asserts, and
   C21 re-asserts for both new relations, that no runtime login can reach it;
3. any change to an evidence-identity column raises `42501`
   *"b24 invalidation evidence identity is immutable after creation"* — for
   **every** runtime principal, the planner included;
4. any change to `source_snapshot_hash` raises `42501` unless the caller holds
   `app_worker` **and** the row is moving `leased → authority_waiting`.

`public.trust_enforce_issuance_history_immutable()`, on
`BEFORE UPDATE OR DELETE ... FOR EACH ROW`: superuser and owner pass (the owner
branch is also what keeps a governed tenant `ON DELETE CASCADE` working);
everything else raises `42501` *"durable trust issuance history is immutable"*.

The trigger is named `trg_b24_dirty_event_authority` so it sorts before
`trg_b24_enforce_dirty_event_lifecycle`: a statement that violates both rules
reports the authority refusal, which is the load-bearing one, and the C7
assertion on `b24_dirty_event_observed_at_immutable` is untouched because
`observed_at` is deliberately left to the guard that already owns it.

### Layer 0 — the authority contract

`AUTHORITY_CONTRACT` in
`backend/tests/trust/test_b25_p13_c20_runtime_authority.py` now names all five
trust-bearing relations. It is asserted as an **equality**, not a subset, so a
future migration that widens any of them fails there rather than in an audit.
`test_c21_new_consequence_relations_are_inside_the_authority_contract` asserts
the C21 relations are present with the expected shape, so quietly deleting one
from the contract fails too. Both defects survived because that map was derived
from the relations someone had already thought about.
