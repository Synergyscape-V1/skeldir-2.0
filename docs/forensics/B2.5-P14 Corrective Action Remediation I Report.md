## 0. What this corrective is, in one paragraph

Two independent audits looked at the same protected main and disagreed about one
thing. Both confirmed that Corrective XXI's two named defects are genuinely
closed and physically re-verified. Audit 66 also observed that a well-formed
`status='success'` row could be inserted into `trust_envelope_issuance_log` by
any principal holding INSERT, classified it as bounded hardening debt on the
grounds that the fabrication is cryptographically distinguishable, and passed the
phase. Audit 67 asked the narrower question — *which* principals hold that
INSERT, and does any of them have a causal reason to — found `app_worker` among
them, executed the fabrication as the real worker login, received `INSERT 0 1`,
and failed the phase on it. Audit 67 is right, and this corrective closes it: not
by revoking the grant the auditor used, but by deriving the authority from the
consequence graph. Durable issuance history is now (a) writable only by the
principal that causally records it, (b) referentially bound to the audit ledger
record it projects, and (c) required to agree with that record field by field.
On top of that closure, this change implements the rest of the P14 conjunction —
the four canonical projection profiles, the B2.7 explanation conservation
adjudicator, and the B2.8 request-driven simulation boundary — each with
falsifiers that have physically gone red for the predicted cause and green again
after exact restoration.

## 3. Initial findings

### F-P14-01 (dispositive, inherited) — durable issuance history was fabricable

**Reproduced before anything was changed.** On a freshly provisioned PostgreSQL 15
universe replayed empty→head at `202609031200`, with the production role graph
built by `scripts/database/prepare_migration_authority_boundary.py`, connected as
the real `app_worker` login with a legitimate tenant GUC bound:

```
INSERT INTO public.trust_envelope_issuance_log
  (tenant_id, access_audit_ref, idempotency_key_hash, subject_type,
   subject_ref_hash, envelope_hash, semantic_truth_hash, policy_state,
   audit_ref, audit_hash, status)
VALUES (..., 'success');
```

**Result: `INSERT 0 1`.** The same statement also succeeded as `app_user`. Every
other production principal (`app_dispatch_publisher`, `app_celery_transport`,
`app_trust_issuer`, `app_trust_signer`) was refused `42501` — so the fabrication
surface was exactly `app_user` and `app_worker`, matching audit 67's own scan.

**Root cause, traced rather than assumed.** Migration `202607011200` granted
`SELECT, INSERT, UPDATE` on all four trust audit relations to `app_user` *and*
`app_rw`. Corrective XXI removed UPDATE from both heads but deliberately retained
INSERT on `app_rw`, and said why in its own docstring: *"the C9
positive-confidence lane composes [a Trust read] under the worker principal."*
That CI job (`b2-5-p13-c9-positive-confidence`) sets `DATABASE_URL` to
`app_worker` credentials for its entire process because the same process also
samples the posterior inline. That is a harness convenience, not a fact about the
deployed topology. Independently confirmed against current source:

- `grep` across `backend/app/tasks/` for `record_trust_audit_event`,
  `_insert_issuance_log`, `build_unsigned_trust_envelope_with_audit`,
  `trust_api`, `trust_export`: **zero matches**.
- The one worker-reachable issuance-adjacent function,
  `reconcile_stale_trust_issuance_states`, uses the dedicated
  `trust_issuance_session_factory()` (`app_trust_issuer`) and never touches
  `trust_envelope_issuance_log`.
- `docker-compose.c19.yml`: only the `api` container receives
  `TRUST_ISSUANCE_DATABASE_URL`; the Bayesian and B2.3 workers receive only
  `C19_WORKER_DATABASE_URL` and have no route to the FastAPI trust surface.
- The only production writer of the relation is `app/api/trust_export.py:321`,
  which calls `build_unsigned_trust_envelope_with_audit(..., access_log_only=False)`
  under the API session factory. `app/api/trust_api.py:570` passes
  `access_log_only=True` and does not write it at all.

`app_worker` therefore had no causal responsibility for the relation.

### F-P14-02 (this audit's own finding, deeper than the grant) — the terminal record was bound to nothing

Fencing the principal alone would have left a larger property unstated. Before
this change, `access_audit_ref` was free text with no referential constraint: a
fabricated row could name an audit record that never existed, and the schema had
no way to tell the difference. `app_user` — the lawful writer — could therefore
still assert durable issuance history that disagreed with, or was unrelated to,
the audit ledger. Audit 66 recorded the row-level indistinguishability as bounded
debt; this corrective treats it as the same defect class as F-P14-01 and closes
it structurally rather than by argument.

### F-P14-03 — the P14 contract floor did not exist

The original B2.5 hierarchy defines P14-G1..G4 as completion gates. Nothing in
the repository implemented them: no projection profile registry, no explanation
conservation surface, no simulation admission boundary. Grepping `backend/app`
for `projection_profile`, `llm_explanation_projection`,
`optimization_projection` returned nothing. P14 was, at entry, entirely unbuilt
beyond the inherited Gate 0 debt.

## 4. Gate 0 remediation and its proof

Authority is expressed three times, for the reason Correctives XX and XXI
established empirically: a later migration that re-grants a historical privilege
must not silently restore the historical capability.

**Layer A — privilege.** `REVOKE ALL … FROM app_rw` on
`trust_envelope_issuance_log`, `trust_replay_events` and
`trust_scope_denial_events`, re-granting `SELECT` only; `app_user` keeps a direct
`SELECT, INSERT`. `app_worker` holds no direct grant on any of the three, so this
removes its entire effective write authority there. The two sibling relations are
narrowed for the same reason and by the same code path — audit 67's forward
obligation 2.

**Layer B — referential binding.** A real foreign key
`(tenant_id, access_audit_ref) → trust_access_log(tenant_id, audit_ref)
ON DELETE CASCADE`. The migration first counts unbound pre-existing rows and
raises `23503` rather than validating around them, because those rows are
precisely the class the constraint exists to make impossible.

**Layer C — consequence guard.** `trg_trust_issuance_consequence_authority`,
`BEFORE INSERT FOR EACH ROW`, refuses unless the caller is a member of `app_user`
(or is the owner/superuser, either of which can drop the trigger anyway), *and*
the referenced ledger row is an `issuance`/`success` record whose
`idempotency_key_hash`, `subject_type`, `subject_ref_hash`, `envelope_hash`,
`semantic_truth_hash`, `policy_state` and `audit_hash` agree exactly with the row
being written. `record_trust_audit_event` writes both rows from one
`_params(...)` mapping inside one transaction, so agreement is automatic on the
lawful path and has to be manufactured on any other.

## 5. The canonical contract floor (P14-G1 … P14-G4)

`contracts/trust-api/projection-profiles.v1.yaml` is a versioned,
machine-inspectable registry loaded fail-closed by
`backend/app/trust/projection_profiles.py`. Unknown profile ids, unknown field
paths, unknown trust classes, unknown positions and missing matrix cells are
errors, not defaults.

Each profile carries a **content-addressed identity**: `profile_hash` is a tagged
SHA-256 over the profile's canonical form, excluding only its prose `purpose`.
An editorial clarification therefore leaves the identity stable, while any change
to what a profile *permits* moves it — proved by mutating the real registry both
ways and comparing hashes. A stored explanation or simulation names the exact
bytes of the contract it was produced under, which is what makes Gate 12's
reconstruction requirement a property of the data.

### 5.1 P14-G1 — all four required profiles exist

`llm_explanation_projection_safe`, `optimization_projection_safe`,
`audit_projection_internal`, `display_projection_untrusted_labels_allowed`, all
`status: supported`, all versioned, all hashed (§1).

**Falsifier (Gate 1):** remove `optimization_projection_safe` from the real
registry → loader raises `projection_profile_required_missing`, the static gate
exits 1 → restore → green. Physically executed as `NC-P14-03`.

### 5.2 P14-G2 — the default LLM projection excludes untrusted labels

Expressed as arithmetic rather than as a policy sentence. Every text trust class
has a maximum position; provider-controlled classes cap at `display_only`; the
loader refuses any field seated above its class's ceiling. Separately, the
default LLM profile must admit no provider-controlled class *at all*, and nothing
in it reaches above `policy`.

Verified behaviourally against the shipped
`prompt_control_string_quarantined` contract example: the projection contains no
`untrusted_display_data.*` path, and the composed explanation's narrative does
not contain the provider string. The audit profile, which *may* see it, seats it
at `display_only`.

**Falsifiers (Gate 1):** (a) append the quarantined label to the LLM profile →
`projection_untrusted_label_not_admitted`; (b) promote the label to `instruction`
in the audit profile → `projection_position_exceeds_trust_class`. Both restore
green. (a) is physically executed in CI as `NC-P14-04`.

### 5.3 P14-G3 — policy authority remains typed

Every profile declares `policy_authority_projection: typed`, and every
`policy_action_authority.*` field is seated at `position: policy` with
`trust_class: machine_authority_enum`. A policy state outside the source enum is
refused at projection time (`policy_state_untyped`), so free text cannot occupy
an authority position. `assert_authority_monotonic` permits equality and
reduction and refuses every escalation the directive enumerates
(`simulation_only → approval_required`, `blocked → simulation_only`, …).

**Falsifier:** set `max_action_authority: approval_required` on the optimization
profile → `projection_action_authority_forbidden` → restore → green.

### 5.4 P14-G4 — LLM-as-Judge remains non-authoritative

Structural, not promissory. `judge_authority` and
`llm_authority_over_projected_values` must equal `none` in every profile or the
registry does not load. `assess_presentation` returns a `JudgeAssessment` that
carries no truth-bearing field, and there is no function anywhere that consumes
one to modify an `ExplanationResult` — asserted by reading the module source in
the test. Scoring an explanation leaves it byte-identical. The database restates
it: `b27_explanation_materializations` has `CHECK (judge_authority = 'none')`.

**Falsifier:** grant `judge_authority: may_override_confidence` →
`projection_judge_authority_forbidden` → restore → green.

## 6. B2.7 — explanation semantic conservation

An explanation is a typed set of **claims**, each bound to an authoritative
source path, with the narrative rendered *from* the claims. That inversion is the
design: an unsupported number has nowhere to live, because it is not in the claim
set. `adjudicate_explanation_conservation` is a checker over a finished artifact
rather than a filter inside a generator, so it decides correctly about an
artifact a mutated renderer — or a future LLM — produced.

All eight Gate 5 source states (confidence available, unavailable, degraded,
diagnostics-failed, stale/fallback, non-causal attribution, malicious provider
label, revenue claim) compose and conserve against real shipped contract
examples.

| directive hypothesis | adversarial artifact | refused with |
|---|---|---|
| H-P14-E1 unsupported financial number | narrative asserting `987654` minor units | `unsupported_financial_number:987654` |
| H-P14-E1 mutated financial claim | claim value = source + 1 | `claim_value_mutated:verified_revenue_minor` |
| H-P14-E1 claim on an unprojected path | claim bound to `signature` | `claim_source_not_projected` |
| H-RC7 float money | `verified_revenue_minor = 123.45` | `projection_float_forbidden` |
| H-P14-E2 causal claim | typed `causal_statement` claim | `causal_claim_without_authorizing_substrate` |
| H-P14-E2 causal language | five distinct causal phrasings | `causal_language_in_narrative` |
| H-P14-E3 suppressed unavailability | confidence-status claim stripped | `confidence_unavailability_not_stated` |
| H-P14-E3 confidence upgrade | "we are highly confident" under `unavailable` | `confidence_claim_under_unavailable_state` |
| H-P14-E3 score inflation | score + 500 bp | `claim_value_mutated` |
| H-P14-E4 fallback suppression | fallback claims stripped | `fallback_state_suppressed` |
| H-P14-E5 instruction ingress | provider text with an injected quantity | `instruction_context_unbound_numeric` |
| Gate 8 escalation | `read_only → approval_required` | `authority_escalation_forbidden` |
| H-P14-DU1 wrong source | result adjudicated against a foreign projection | `source_envelope_mismatch` |
| H-P14-E7 cross-tenant | result adjudicated against a foreign tenant | `source_tenant_mismatch` |

**A real defect found in the checker itself, and corrected.** The first version's
causal indicator matched the bare adjective `causal`, which refused the
renderer's own `causal_status` sentence — the one statement whose purpose is to
say that causality was *not* estimated. Two corrections were made rather than
loosening the gate: verbatim projections of source values are masked before the
lexical sweep (a value copied from an authoritative field is the source speaking,
and correspondence has already been checked), and the indicator now targets
causal verbs, connectives and asserting noun phrases rather than the field name.
Both changes narrow what is *tolerated in prose the system did not author*; they
do not widen what a claim may assert, which remains structurally gated.

### 6.1 Gate 10 — cache identity and staleness

`compute_cache_identity` closes over nine components: tenant, semantic truth,
policy state, confidence status, confidence authority, causal status, fallback
state, projection profile hash, explanation contract version. Because the
identity is a function of meaning, a lawful `T1 → T2` transition produces a
different key and a stale materialization is *unreachable*, not merely
detectable.

**Every one of the nine is proved load-bearing by measurement, not argument.**
For each component the proof builds a pair of states differing only in it,
requires the full identity to separate them, and requires the identity computed
*without* it to conflate them. No component is skipped.

The database makes the transition observable as well as unreachable:
`trg_b27_supersede_stale_explanations` marks dependent materializations stale
when new issuance history for the same subject carries a different semantic
truth, and leaves them alone when it carries the same one. It is
`SECURITY DEFINER` with a pinned search path, so the staleness marking is a
consequence of issuance rather than a capability the writing principal holds —
which is why no runtime principal holds `UPDATE` on any P14 relation.

Tenant scoping is physical: `UNIQUE (tenant_id, cache_identity_hash)` under FORCE
RLS. Two tenants may hold the same identity without colliding; one tenant may
not hold it twice.

## 7. B2.8 — request-driven simulation and proposal conservation

The admission conjunction lives in one place and the solver has exactly one
caller, enforced statically. The order of conjuncts is deliberate — every earlier
one fails *before* the solver is reachable, so a refusal leaves the physical
invocation count untouched.

```
solver_invoked ⇒ explicit_valid_request
                 ∧ source Trust identity present and agreeing
                 ∧ tenant binding holds
                 ∧ source policy admits simulation
                 ∧ evidence sufficiency passes
```

### 7.1 Gate 6 — sufficiency admits, it does not trigger

The Gate 6 experiment verbatim: prepare a **sufficient** evidence set
(3 channels, 22 conversions, 750 000 minor units — `adjudicate_sufficiency`
returns `sufficient=True`), issue **no** request, and observe.

```
solver invocations = 0
simulation artifacts = 0
proposals = 0
reason_code = simulation_no_explicit_request
```

Then one valid request admits ordinarily (`solver_invocations = 1`).

The specification error is prevented structurally as well as behaviourally:
`sufficiency.py` neither imports nor names the solver, and the static validator
fails the build if it ever does. `b28_simulation_results.request_id` is
`NOT NULL REFERENCES b28_simulation_requests(id)`, so a result *cannot exist*
without the explicit request that authorized it. And no module outside
