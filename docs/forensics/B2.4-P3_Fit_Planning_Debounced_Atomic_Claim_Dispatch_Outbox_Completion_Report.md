## 4. Dirty-Event Design and Contention Proof

Dirty capture is implemented in `backend/app/bayesian/dirty_marker.py` as `append_dirty_event()`.

The hot-path operation is a single `INSERT INTO public.b24_dirty_events` with no upsert, no shared per-window counter row, no snapshot call, no fit claim, and no queue publish. This makes concurrent source bursts append independent rows instead of serializing on one tenant/window marker update.

The P3 validator and tests reject hot-path `ON CONFLICT DO UPDATE`, source snapshot calls, fit claim calls, and broker dispatch calls.

## 5. Dirty-Event Lifecycle and Coalescing Proof

`b24_dirty_events.status` allows:

```text
pending, leased, coalesced, claimed, suppressed, fallback_only, superseded, dispatched, pruned
```

The planner groups pending rows by tenant/model/version/window, leases eligible rows with `FOR UPDATE OF dirty SKIP LOCKED`, and marks leased rows according to the planning result:

- `claimed` after claim plus durable dispatch intent.
- `fallback_only` when P2 source snapshot authority reports insufficient/sparse state.
- `superseded` when a newer hash is desired while an active execution already exists.

## 6. Debounce Policy

- `DEBOUNCE_POLICY_VERSION`: `b24-p3-debounce-v1`
- `QUIET_PERIOD_SECONDS`: `120`
- `MAX_WAIT_SECONDS`: `900`
- `PLANNER_CANDIDATE_LIMIT`: `100`
- `DIRTY_EVENT_LEASE_SECONDS`: `300`

The planner computes no source snapshot until grouped dirty rows are quiet for the quiet period or exceed the max-wait cutoff.

## 7. Active Execution Lock Design

`b24_active_execution_leases` is keyed by:

```text
tenant_id, model_type, model_version, source_window_start, source_window_end
```

The key intentionally excludes `source_snapshot_hash`. Active statuses are `claiming`, `dispatch_pending`, `dispatched`, `running`, and `cancel_requested`.

## 8. Historical Fit Identity vs Active Execution Identity

Historical fit identity remains P1-compatible:

```text
tenant_id + model_type + model_version + source_window_start + source_window_end + source_snapshot_hash
```

Active execution identity is narrower:

```text
tenant_id + model_type + model_version + source_window_start + source_window_end
```

That split preserves audit history by source hash while physically preventing concurrent expensive execution for one tenant/model/window.

## 9. H1/H2 Supersession Proof

When H1 is active and H2 arrives for the same tenant/model/window with a different `source_snapshot_hash`, `claim_fit_for_snapshot()` locks the existing lease row and updates:

```text
latest_desired_source_snapshot_hash = H2
needs_refit_after_current = true
```

It returns `SUPPRESSED_ACTIVE` and does not insert a second active lease. H2 can be claimed only after the existing lease reaches terminal or stale-recoverable state.

## 10. Atomic Claim Mechanism

`claim_fit_for_snapshot()` performs these writes in one caller transaction:

1. Insert or lock the active execution lease.
2. Insert or reuse the P1 historical fit row.
3. Insert or reuse the dispatch outbox row.
4. Move the active lease to `dispatch_pending`.

Python checks are not the authority; the lease primary key and fit/outbox uniqueness constraints are the authority.

## 11. Concurrent Planner Proof

Dirty candidate leasing uses `FOR UPDATE SKIP LOCKED`. Active execution claiming uses the hash-independent active lease key. Racing planners can duplicate neither the active lease nor the outbox intent.

## 12. Transactional Dispatch Outbox Design

`b24_fit_dispatch_outbox` contains:

```text
id, tenant_id, fit_id, dispatch_key, status, attempt_count, max_attempts,
next_attempt_at, last_attempt_at, last_error, dispatching_started_at,
stale_recovered_at, created_at, updated_at, dispatched_at, dead_lettered_at
```

Outbox statuses are:

```text
pending, dispatching, dispatched, failed_retryable, dead_lettered, stale_recovered
```

The outbox has unique constraints on `(tenant_id, dispatch_key)` and `(tenant_id, fit_id)`.

## 13. Claim Plus Dispatch Same-Transaction Proof

The fit row and outbox row are both written by `claim_fit_for_snapshot()` before the caller transaction commits. There is no DB-commit-then-broker-publish path in the planner or deterministic hot paths.

Crash after claim but before broker publish leaves a durable `pending` outbox row for later replay.

## 14. Dispatcher Retry and Recovery Proof

`dispatch_outbox.py` leases due rows with `FOR UPDATE SKIP LOCKED`, marks them `dispatching`, publishes the fit-id-only payload, then marks success as `dispatched`.

Failures become `failed_retryable` until `max_attempts`, then `dead_lettered`. Stale `dispatching` rows are moved to `stale_recovered` with `next_attempt_at = now()`.

## 15. Duplicate Delivery Idempotency Proof

The future worker stub `execute_fit_intent` accepts only `fit_id` and returns an idempotent no-compute acknowledgement. It does not create artifacts, mutate deterministic truth, start sampling, or create new fits. Duplicate outbox publish and duplicate broker delivery are therefore safe in P3.

## 16. Fit-ID-Only Payload Proof

`DispatchOutboxRow.queue_payload` returns:

```json
{"fit_id": "..."}
```

The validator rejects queue payloads containing source rows, source manifests, tenant source data, PII, raw payloads, matrices, or sampling parameters.

## 17. Source Snapshot Query-Plan / Fallback-Index Proof

P3 uses the accepted P2 source snapshot authority. To remove plan ambiguity for planner-invoked source streams, P3 adds non-partial composite fallback indexes for:

- `attribution_events`


The P3 validator and tests assert these fallback indexes exist in the canonical schema and migration.

## 18. Ingress Latency Protection Proof

Ingress adds only one bounded dirty-event insert after deterministic truth has been written. It does not compute P2 snapshots, claim active execution, or publish broker messages. The burst overhead policy is `append_only_single_insert_v1`, and the test suite rejects hot-row compaction in the deterministic path.

## 19. Deterministic Truth Non-Mutation Proof

P3 planner, claim, and dispatch modules do not update B2.1/B2.3 attribution, match verdict, revenue event, or verification source-truth tables. Deterministic modules append dirty events only after their own source-truth writes.
