# B2.4-P5 Remediation Evidence Pack

## Scope

B2.4-P5 is a bounded Bayesian runtime harness. It proves that PyMC, PyTensor, and ArviZ can run in an isolated worker lane with exact runtime identity, native thread caps, process/execution-scoped compiledirs, supervised sampler child termination, child DB/control-plane airgaps, bounded compiledir cleanup, and durable timeout fallback states.

It does not add public attribution APIs, TrustEnvelope output, frontend confidence logic, production attribution semantics, LLM authority, or deterministic-truth mutation.

## Follow-Up Corrective Findings

- The prior P5 evidence was not complete because the live protected branch did not require `B2.4-P5 Bayesian Runtime Harness`; the contract declared the context, but branch protection did not yet enforce it.
- Runtime identity was under-specified: PyTensor was resolver-owned and not directly locked by the Bayesian lane, so the real PyTensor version could drift without a falsifiable runtime check.
- The child sampler environment was not proven as an allowlist. A blacklist/copy-style child environment would allow DB URLs, cloud credentials, or control-plane settings to leak into native sampler children.
- Compiledir isolation was too coarse. Worker-scoped paths did not include parent PID and execution identity, and cleanup lacked a bounded, owner-marker-preserving reaper.
- The parent-death proof was not kernel-real. A supervisor timeout alone does not prove child death when the parent disappears by `SIGKILL`.
- The PyMC sampling policy needed explicit single-process enforcement, not just low default values.
- Timeout fallback proof was log-heavy and did not prove the actual worker helper could persist a tenant-scoped row transition in PostgreSQL.

## Directive II Corrective Findings

Directive II reopened two narrow P5 containment hypotheses after the prior protected merge.

- H-P5-C13 was validated as not fully proven. `sampler_child.py` blocked forbidden imports after module execution began, but the evidence did not prove that the blocker existed at interpreter boot before `-m app.bayesian.sampler_child` resolved `app` and `app.bayesian`, nor did it assert the forbidden `sys.modules` cache before blocker installation.
- H-P5-C14 was validated as not fully proven. The tiny benchmark used `chains=1`, `cores=1`, and `blas_cores=1`, but the sampler child interpreter did not physically deny `os.fork`, default `multiprocessing.Process`, or default/fork multiprocessing contexts.
- No new P6 scope was required. The correction is runtime-cage closure only: interpreter boot, import cache state, fork/default multiprocessing denial, central P5 sampling policy, and non-regression of existing P5 DB/runtime proofs.
