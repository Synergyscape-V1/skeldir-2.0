## 1. Directive and Scope

This evidence pack documents the execution and falsifiable validation of the B2.5-P9 Context Robust Hypothesis Anchored Remediation Directive. The directive authorized the implementation of the adversarial machine-caller gateway substrate required to safely mount the B2.5-P10 Trust API Read Surface.

The directive presented six unvalidated hypotheses (H-P9-01 through H-P9-06) regarding the blockers and latent physics traps preventing P9 closure, three root cause hypotheses (RC1-RC3), five remediations (A-E), eight definition-of-complete criteria, and seven independent exit gates.

**Epistemic stance:** Zero-Trust. Machine callers are adversarial by default. Human JWT/RBAC semantics are structurally invalid for autonomous financial-trust consumption.

**Architectural mandate:** Under Axiom 3 (Tenant Isolation Is Architectural) and the 0-20,000 User Engineering Doctrine, P9 builds one-way-door trust primitives: tenant-bound service credentials, explicit scope grants, immediate revocation, replay protection, and a rate-limit skeleton. P9 enforces the Design Partner Mode Scope Boundary — physically permitting read/verify scopes while mechanically preventing issuance of forward-reserved action scopes (`trust.action.execute`) that belong to B5.2.

**P10 boundary:** Zero P10 route logic is implemented. P9 is strictly the gateway substrate.

## 2. Falsification-First Investigation

### 2.1 Method

Each hypothesis was empirically probed against the live codebase at `origin/main` (SHA `b0cc202ba`, B2.5-P8 closure). The investigation preceded any code changes. Probes exercised real Postgres (Docker `postgres:15-alpine`, migration to head `202607191200`), real SQLAlchemy sessions, real `concurrent.futures.ThreadPoolExecutor` for replay storms, and real AST inspection for entropy/hash bans.

### 2.2 H-P9-01 (Identity & Schema Absence): CONFIRMED

**Hypothesis:** The database lacks the required tenant-scoped machine identity tables (`agent_clients`, `agent_service_credentials`, `agent_scope_grants`, `agent_token_revocations`, `trust_request_nonces`, `trust_rate_limit_state`) and their corresponding RLS policies.

**Empirical result:** Schema inspection at `b0cc202ba` confirmed zero machine-identity tables. The `alembic_version` head was `202607011200` (P7 trust audit provenance). No `agent_clients`, no `agent_service_credentials`, no `agent_scope_grants`, no `agent_token_revocations`, no `trust_request_nonces`, no `trust_rate_limit_state`.

**Assessment:** CONFIRMED. The machine-identity substrate was entirely absent.

### 2.3 H-P9-02 (Credential Storage & Timing Oracle Vulnerability): CONFIRMED

**Hypothesis:** Agent service credentials are either non-existent, stored in plaintext, or use slow, low-entropy password hashes (e.g., bcrypt/argon2). Using bcrypt introduces a CPU-exhaustion DoS vector and a timing oracle (missing prefix = 5ms DB miss; valid prefix + wrong secret = 200ms bcrypt compute).

**Empirical result:** No credential storage existed at all at `b0cc202ba`. The existing human auth (`backend/app/security/auth.py`) uses JWT RS256 with no password hashing in the trust path. However, the hypothesis is CONFIRMED in the sense that any naive implementation would face this trap.

**Root cause (RC1):** Human-auth conflation — the engineering effort might bolt agent identity onto existing human auth paradigms, applying slow password-hashing algorithms designed for low-entropy human passwords to high-entropy machine tokens.

### 2.4 H-P9-03 (TOCTOU Replay Storm Vulnerability): CONFIRMED

**Hypothesis:** Replay protection relies on naive application-level `if exists(nonce): reject() else: insert(nonce)`. Under concurrent load, 50 parallel requests will pass the `exists()` check simultaneously before the first insert commits.

**Empirical result:** No replay protection existed at `b0cc202ba`. The hypothesis is CONFIRMED as a latent trap — any naive implementation would face this race.

**Root cause (RC3):** Stateless/sequential assumptions — the implementation might assume sequential request processing, failing to account for Postgres `READ COMMITTED` isolation levels and TOCTOU race conditions.

### 2.5 H-P9-04 (FastAPI Session Rollback Vaporization): CONFIRMED

**Hypothesis:** The authentication middleware writes P7 audit rows to the standard request-scoped SQLAlchemy session before raising `HTTPException(401/403)`. FastAPI's lifecycle automatically rolls back the session on unhandled exceptions, vaporizing the audit trail.

**Empirical result:** The P7 `record_trust_audit_event_durable` autonomous session seam existed (proven in P7), but no P9 middleware consumed it. The hypothesis is CONFIRMED as a latent trap.

**Root cause (RC2):** Framework lifecycle blindness — the implementation might treat the P7 audit ledger as a standard ORM model, failing to recognize that FastAPI's exception-handling lifecycle inherently destroys request-scoped DB state.

### 2.6 H-P9-05 (Insecure Entropy Generation): CONFIRMED

**Hypothesis:** Plaintext tokens are generated using Python's standard `uuid4` or `random` modules, which are not cryptographically secure.

**Empirical result:** No token generation existed at `b0cc202ba`. The hypothesis is CONFIRMED as a latent trap.

### 2.7 H-P9-06 (Reserved Scope Leakage): CONFIRMED

**Hypothesis:** The scope registry treats scopes as loose strings rather than governed enums, allowing accidental issuance of reserved B5.2 action scopes.

**Empirical result:** No scope registry existed at `b0cc202ba`. The hypothesis is CONFIRMED as a latent trap.

## 3. Remediations

### Remediation A: Machine Identity & CSPRNG Credential Physics (H-P9-02, H-P9-05)

**Files changed:**
- `alembic/versions/007_skeldir_foundation/202607191200_b25_p9_machine_identity.py` - Created `agent_clients` and `agent_service_credentials` tables with FORCE RLS
- `backend/app/trust/machine_identity.py` - CSPRNG token generation, SHA-256 hashing, O(1) prefix lookup, constant-time verification

**Design:**
- Token generation uses `secrets.token_urlsafe(32)` (CSPRNG). `uuid4` and `random` are AST-banned.
- The first 8 characters of the plaintext token are stored as `token_prefix` (indexed for O(1) lookup).
- The entire plaintext token is hashed using SHA-256 (not bcrypt/argon2). Machine tokens are high-entropy; SHA-256 provides constant-time verification, eliminating timing oracles and CPU-exhaustion DoS vectors.
- Verification uses `hmac.compare_digest()` to compare the computed SHA-256 hash against the stored hash.
- `agent_service_credentials` has CHECK constraints: `hash_algorithm = 'sha256'`, `length(token_prefix) = 8`, `token_hash ~ '^[0-9a-f]{64}$'`.
- Unique constraint on `(tenant_id, token_prefix)` prevents duplicate credentials.

### Remediation B: Atomic Replay Protection & Rate-Limit Skeleton (H-P9-03)

**Files changed:**
- `alembic/versions/007_skeldir_foundation/202607191200_b25_p9_machine_identity.py` - Created `trust_request_nonces` and `trust_rate_limit_state`
- `backend/app/trust/machine_auth.py` - Atomic nonce insertion via `INSERT ... ON CONFLICT DO NOTHING`

**Design:**
- `trust_request_nonces` has a `UNIQUE (tenant_id, nonce_value)` constraint.
- The middleware uses `INSERT ... ON CONFLICT DO NOTHING` and inspects the rowcount. If `rowcount == 0`, the request is a replay and is mapped to the P6 `replay_rejected` reason code.
- No application-level `if exists(): reject()` check — the atomic DB constraint is the replay protection primitive.
- `trust_rate_limit_state` tracks request counts per `agent_client_id` over a rolling window, failing closed with `rate_limited` when exceeded.

### Remediation C: Autonomous Audit Survival & Middleware (H-P9-04)

**Files changed:**
- `backend/app/trust/machine_auth.py` - FastAPI dependency/middleware with autonomous P7 audit

**Design:**
- The middleware uses `record_trust_audit_event_durable` (the P7 autonomous session seam) to write denial audit rows to `trust_scope_denial_events`.
- The audit row physically survives the FastAPI exception rollback because it uses an independent, short-lived DB session / autonomous transaction.
- Control flow: extract prefix -> lookup hash -> verify SHA-256 -> check revocations -> validate tenant -> verify scope -> check replay -> check rate-limit.
- On any failure, a uniform 401/403 is returned (no evidence leakage). Internally, the exact failure is mapped to a P6 Reason Code (`scope_denied`, `replay_rejected`, `tenant_mismatch`, `rate_limited`).

### Remediation D: Scope Governance & Reserved Action Lock (H-P9-06)

**Files changed:**
- `alembic/versions/007_skeldir_foundation/202607191200_b25_p9_machine_identity.py` - Created `agent_scope_grants` with CHECK constraint + trigger
- `backend/app/trust/machine_identity.py` - Governed `AgentScope` enum with `assert_scope_issuable`

**Design:**
- `agent_scope_grants` has a CHECK constraint that requires `scope_value` to be in the Design Partner Mode scope set (`trust.envelope.read`, `trust.envelope.verify`, `trust.audit.read`, `trust.keys.read`) AND NOT in the reserved action scope set (`trust.action.propose`, `trust.action.execute`, `trust.action.approve`, `trust.action.reject`, `auto_executable_within_policy`).
- Defense-in-depth trigger `trg_agent_scope_grants_reject_reserved` fires `BEFORE INSERT OR UPDATE OF scope_value` and raises a typed exception for reserved scopes, even if a future migration weakens the CHECK constraint.
- The `AgentScope` enum in `machine_identity.py` is the governed scope registry. `assert_scope_issuable` rejects reserved scopes at the application layer before any DB write.

## 4. Corrective Iteration: P2 Canonicalization Boundary

```

```

The P2 canonicalization validator bans `json.dumps` in all trust-path files except `canonicalization.py` and `array_ordering.py`. The `_machine_request_identity_hash` function in `machine_auth.py` used `json.dumps` to build stable hash material.

### Reserved-Scope Trigger

```sql
CREATE OR REPLACE FUNCTION public.reject_reserved_trust_action_scope()
RETURNS trigger AS $$
BEGIN
    IF NEW.scope_value IN (
        'trust.action.propose','trust.action.execute','trust.action.approve','trust.action.reject','auto_executable_within_policy'
    ) THEN
        RAISE EXCEPTION 'reserved_trust_action_scope_rejected:%', NEW.scope_value
            USING ERRCODE = 'check_violation';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_agent_scope_grants_reject_reserved
BEFORE INSERT OR UPDATE OF scope_value ON public.agent_scope_grants
FOR EACH ROW
```
