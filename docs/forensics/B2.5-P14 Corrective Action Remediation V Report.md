## 1. What was actually wrong

### 1.1 Reproduction on the entering tree, before any remediation

Every blocking hypothesis was independently reproduced on tree `795b4ddc` at head
`202609051200`, on a database built empty→head by the repository's own role
script, using the real least-privilege `app_user` login through pure SQL with no
application call anywhere in the path.

```text
REQ_DIRECT_SQL_NO_INTENT      ALLOWED rowcount=1  requested_by='attacker:not-a-real-caller'
REQ_EMPTY_REQUESTED_BY        ALLOWED rowcount=1  requested_by=''
RESULT_FORGED_NO_SOLVER       ALLOWED rowcount=1  solver_invocations=1, channels 'a'/'b'
RESULT_SOLVER_INVOCATIONS_99  ALLOWED rowcount=1  solver_invocations=99
PROPOSAL_ON_FORGED_RESULT     ALLOWED rowcount=1
REQUEST_PERSISTED_COLUMNS     id,tenant_id,request_ref,requested_by,source_envelope_id,
                              source_semantic_truth_hash,input_snapshot_hash,
                              total_budget_minor,currency,channel_count,
                              sufficiency_policy_version,requested_at,
                              source_issuance_envelope_hash
CHANNEL_EVIDENCE_RETAINED     False
```

and the effective privilege graph:

```text
app_user  b28_simulation_requests  S,I
app_user  b28_simulation_results   S,I
app_user  b28_proposals            S,I
```

That maps onto the directive's hypotheses as: **H-V-01 validated** (a durable
request does not prove intent), **H-V-02 validated** (`requested_by` is
descriptive text — and, beyond both audits, is not even non-empty), **H-V-03
validated** (one authority domain writes cause and consequence), **H-V-04
validated** (a result does not prove the solver ran, and the invocation count is
free), **H-V-05 validated** (sufficiency was never adjudicated at the durable
boundary), **H-V-06 validated** (`CHANNEL_EVIDENCE_RETAINED=False` — the input
was not merely unhashed, it was *not retained*, so post-hoc recomputation was
impossible in principle), **H-V-07 validated** (the proposal conserves a
fabricated root exactly), and **H-DU-V-01 / H-DU-V-02 validated** (the honest
application path and the direct database path produce the same durable state).

### 1.2 Root cause

One shape, appearing twice.

**Authority was assigned by relation membership instead of causal
responsibility.** The generic API principal held INSERT on all three B2.8
relations, so a single credential could author the alleged cause *and* the
alleged consequence. This is structurally the issuance self-certification defect
that C16/C19 closed for `trust_envelope_issuance_log`, applied to P14's own
relations — and it was closed there the same way it is closed here: by giving the
consequence its own login principal, with the guard keyed on `session_user`,
which `SET ROLE` cannot forge.

**The guards compared rows instead of deriving facts.** The Corrective IV result
guard checks that a result *agrees with* its request — same envelope, same
budget, same snapshot string, governed profile name. Agreement is necessary and
not sufficient. Nothing recomputed anything, so `requested_by`,
`input_snapshot_hash`, `solver_invocations` and `allocations` were all values the
writer chose, and the database had no way to disagree.

The instructive contrast is B2.7, which neither audit could fabricate. Its guard
does not compare the narrative to anything — it *re-derives* the narrative from
the registered frame corpus and requires equality. That is the physics this
corrective brings to B2.8.

## 2. The remediation

Six layers, each independently severable and each independently falsified below.

### 2.1 The request is a complete input witness (H-V-06, Exit Gate 4)

`b28_simulation_requests` now retains `channel_evidence jsonb` — the exact
governed evidence set the request was admitted over — plus the governed
`solver_profile`, the adjudicated sufficiency verdict and its observed counts,
the authenticated requester's two foreign keys, and the writing principal.

`input_snapshot_hash` stops being a string the writer chooses. The database
recomputes it: `b28_canonical_input_material` reproduces
`app.simulation.admission.compute_input_snapshot_hash` byte for byte —
`json.dumps(sort_keys=True, separators=(',',':'), ensure_ascii=False)` over the
same material, SHA-256, `sha256:` tag — and the guard refuses any row whose
stored hash is not the hash of its own stored inputs.

Key ordering is emitted literally in code-point order rather than sorted at
runtime, so it is auditable by reading; string values are escaped with
`to_jsonb(text)::text`, whose escaping rules are exactly Python's under
`ensure_ascii=False`.

**Differential evidence**: 400 randomised trials over 1–6 channels, budgets
`1 … 9 007 199 254 740 740`, punctuation-heavy channel ids, zero-revenue and
zero-conversion channels — the PL/pgSQL twins equal the Python authorities on
every trial for the snapshot hash (400/400), the sufficiency adjudication
(400/400) and the allocation (395/395; the remaining five have no positive
revenue, where the solver is undefined in both implementations). A 120-trial
version of the same corpus is merge-blocking in
`test_p14_r5_database_derivations_equal_the_application_authorities`.

### 2.2 Requester identity is derived, twice, by two authorities (H-V-01, H-V-02, Exit Gate 1)

The correction is not a longer validation of the string; the string stops being
an input.

* **At the library boundary.** `authenticate_simulation_requester` is the
  counterpart of the P9 HTTP gateway for the surface Design Partner Mode
  actually exposes. It reuses P9's credential physics unchanged — O(1) prefix
  lookup, SHA-256 at rest, `hmac.compare_digest` verification, explicit
  revocation, status and expiry checks — and returns a `VerifiedRequester` whose
  fields are `agent_client_id`, `credential_id`, `tenant_id`, `token_prefix`.
  There is deliberately no display or label field, and no function in the module
  accepts a `requested_by` argument. This answers audit 71 §10's exact finding
  ("no caller authentication exists at the library boundary") rather than
  deferring it to a future ingress.

* **At the database.** The row must name a live `agent_service_credentials` row
  and its `agent_clients` parent, both in the same tenant, `status='active'`,
  not revoked, not expired — and `requested_by` must equal
  `'agent_client:' || requested_by_agent_client_id`, which the guard computes
  and a total `CHECK` constraint restates.

The two derivations cannot both be the caller, so whatever the writer types must
equal what the database derives from a principal that really exists and is
really live. Expiry is compared against the database's clock in both places: two
clocks would be two universes.

### 2.3 Sufficiency is a durable adjudication (H-V-05, Exit Gate 3)

`b28_adjudicate_sufficiency` mirrors `adjudicate_sufficiency`, including the
order and exact text of the reason codes, so an auditor reconstructs the decision
from the persisted numbers alone. The request guard refuses a row whose recorded
verdict, reasons or observed counts differ from the adjudicator's. The result
guard requires `sufficiency_verdict = true`. An insufficient request has no
representable consequence — and the request itself is still recorded, honestly,
as having failed.

### 2.4 The allocation is recomputed, not compared (H-V-04, H-RC-V-03, Exit Gate 2)

The solver is a deterministic integer function — largest remainder over verified
revenue, weights in basis points, ties broken by channel id — so the database can
evaluate it. `b28_recompute_allocation` is a PL/pgSQL twin of
`app.simulation.solver.allocate_budget`; the result guard runs it over the
request's own retained evidence and requires the persisted allocation to be
exactly its output, line for line, including weights and order. Numerators are
`numeric` because Python integers are unbounded and `revenue × budget` overflows
`bigint` at design-partner magnitudes.

A fabricated allocation is not refused because it looks wrong. It is refused
because it is not the value of the function:

```text
b28_result_not_solver_consequence:
  [{"channel_id":"channel0","allocation_minor":1000,"weight_basis_points":10000},
   {"channel_id":"channel1","allocation_minor":0,"weight_basis_points":0}]
vs
  [{"channel_id":"channel0","allocation_minor":333,"weight_basis_points":3333},
   {"channel_id":"channel1","allocation_minor":667,"weight_basis_points":6667}]
```

`solver_invocations` must be exactly 1. A lawful admission runs the solver once,
so 99 is now as unrepresentable as 0.

**What this proves, stated precisely.** For a deterministic function, the
strongest available consequence claim is extensional: the persisted allocation
*is* the governed solver's output on the admitted input, and no other value is
representable. A forger would have to reimplement the governed algorithm
bit-for-bit, at which point the value is the solver's consequence by extension.
This is deliberately not a cryptographic witness over self-asserted metadata:
such a witness remains self-certifiable by whoever holds the key, which is
Directive V's own H-RC-V-08.

### 2.5 Authority follows causal responsibility (H-V-03, H-RC-V-01, H-RC-V-02, Exit Gate 8)

`app_user` loses INSERT on all three B2.8 relations and keeps SELECT — reading a
simulation is a read. Two dedicated least-privilege logins carry the two claims,
and the guards compare `session_user` to them:

| Relation | app_user | app_worker | app_rw | app_ro | app_b28_requester | app_b28_solver |
|---|---|---|---|---|---|---|
| `b28_simulation_requests` | S | S | — | S | **S,I** | S |
| `b28_simulation_results` | S | S | — | S | — | **S,I** |
| `b28_proposals` | S | S | — | S | — | **S,I** |
| `b27_explanation_materializations` | S,I | S | — | S | — | — |
| `trust_envelope_issuance_log` | S | S | S | S | S | S |

Both new principals: `rolsuper=false`, `rolbypassrls=false`, `rolcreaterole=false`,
`rolcreatedb=false`, and members of **nothing** — so no runtime principal reaches
either by inheritance, and neither reaches the other. No principal holds UPDATE or
DELETE on any downstream relation, at the privilege layer, before any trigger runs.

B2.7's privileges are deliberately unchanged: its persistence gate passed both
independent audits, and its guard already has the derivation physics this
corrective brings to B2.8. Narrowing it would have been scope beyond the
demonstrated failure.

### 2.6 Operational wiring (H-WIRE-V-01, H-WIRE-V-02, H-ART-V-03, Exit Gate 11)

`app/simulation/persistence.py` is the only writer of B2.8 durable state, and
`conduct_requested_simulation` is the whole lawful path:

```text
presented credential
  → authenticate_simulation_requester   (verified principal, under request custody)
  → persist_simulation_request          (app_b28_requester)  → durable request
  → simulate_from_trust                 (admission conjunction → the real solver)
  → persist_simulation_consequence      (app_b28_solver)     → result + proposal
```

It takes a *token*, not an identity, so there is no argument through which a
caller could name itself. `consequence_custody` fences each DSN to that module
by caller name — the same construction `signer_session.py` uses — and verifies
`session_user` at connect time, so a deployment that authenticates as the wrong
principal fails with a named error at startup rather than a confusing permission
error later:

```text
REFUSED b28_consequence_custody_wrong_principal:app_user!=app_b28_solver
```

The DSNs are exported by the `setup-postgres-ci` composite action for every job
that provisions the boundary, and carried by the C19 production topology, on the
same footing as issuance and signer custody.

## 3. Exit Gate 13 — one definition of a production database

### 3.1 The determination, and why it follows from the artifact

Audit 70 failed Gate M because a database built through
`db/schema/canonical_schema.sql` does not satisfy the repository's own authority
validator. **That measurement was correct.** What was missing was a stated,
checkable ontology: the repository treated the file as a structural reference
(its comparator says so, its CI passed `--structural-only`) while
`docs/database/REMEDIATION-B0.3-GOVERNANCE-SYSTEM-DESIGN.md` ranked it
*"Authority Level: Authoritative (Executable Spec)"* with the migration chain as
*"Derived (Procedural)"* — the exact inverted ontology the audit read.

The file is produced by `pg_dump --schema-only --no-owner --no-privileges`.
Three consequences follow from the generator, not from preference:

* `--no-privileges` means it has **no vocabulary** for grants or ownership, so
  it cannot construct an authority graph;
* `--schema-only` means it carries **no rows**, so every content-addressed seed
  is absent and B2.7 fails closed with `registry_unknown`;
* `alembic_version` is created **empty**, so a database built this way is at no
  revision, and `alembic upgrade head` against it replays from zero into objects
  that already exist.

### 3.2 The measurement

head `202609061200`:

### 3.4 A real product defect, confirmed

Audit 70 recorded that raw `psql -f db/schema/canonical_schema.sql` failed with
`relation "public.users" does not exist`, and classified it as a product defect.
Audit 71 did not reproduce it, because CI supplied
`SET check_function_bodies = false` before loading.

**Audit 70 was right.** The checked-in artifact had its entire pg_dump preamble
stripped — 3 142 comment lines and every `SET`, including
`SET check_function_bodies = false;`. The file therefore could not load in the
order it was itself emitted in: its first object is a SQL-language SECURITY
DEFINER function whose body references `public.users`, which does not exist yet.
Reproduced here on the entering tree, plain `psql -f`, no flags:

```text
psql:/tmp/canon_head.sql:25: ERROR:  relation "public.users" does not exist
LINE 10:             FROM public.users AS u
```

The artifact is regenerated as a faithful `pg_dump` with its preamble intact and
now loads cleanly with no loader-supplied flags (`rc=0`). Both CI canonical-load
steps have had the compensating flags **removed**, so the defect cannot recur
silently, and the construction-authority suite asserts the preamble is present.

Seven were generated; the two highest-consequence were behaviourally

**OW-V-2 — The checked-in canonical artifact was not a faithful pg_dump.**

## 11. Final falsifiable proposition

On this candidate, the narrowest proposition the evidence supports is:

> A durable B2.8 request exists only because a caller proved custody of a live
> machine credential, and its requester identity is derived from that credential
> by two authorities that cannot both be the caller. A durable B2.8 result exists

> to it — for a request whose sufficiency the database itself adjudicated. Neither
> claim is writable by any generic runtime principal, at the privilege layer
> before any trigger runs and at the guard layer if a grant regression restores
> it. Every one of these properties has a control that turns it red by mutating
> real governing state and green again on exact restoration; all of them hold
> inside the unmodified production image; and there is now one falsifiable
> definition of a correctly constructed production database, with the structural
> reference physically unable to serve as one.
