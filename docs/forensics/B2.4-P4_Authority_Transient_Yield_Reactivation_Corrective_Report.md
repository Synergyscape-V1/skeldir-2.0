## 5. Previous `fallback_only` Authority Failure Path

Before this correction, `plan_candidate()` caught `FeatureAuthorityUnavailable`, persisted a feature-authority fallback fit, called `terminalize_preflight_lease(... terminal_status="fallback_only")`, and marked dirty events `fallback_only`. That preserved no-dispatch safety but consumed valid fit intent when the authority was only late.

## 6. New Authority-Yield State Machine

```text
FeatureAuthorityUnavailable
-> request_feature_authority_build()
-> release/terminalize preflight lease with no fit_id
-> leased dirty events become authority_waiting
-> authority builder writes fresh snapshot-matching authority
-> reactivate_planner_for_feature_authority()
-> existing authority_waiting rows become authority_retry_ready
-> one pending feature_authority_fresh dirty marker is inserted idempotently
-> normal planner preflight lease/P2/P4/P3 flow resumes
```

Retry exhaustion terminalizes as `authority_timeout`; explicit build failure terminalizes as `authority_build_failed`. First-pass missing/stale/mismatched authority no longer becomes `fallback_only`.

## 7. Authority-Build Request Mechanism

`request_feature_authority_build()` upserts `public.b24_feature_authority_build_requests` by:

```text
tenant_id
model_type
model_version
source_window_start
source_window_end
source_snapshot_hash
```

The request stores `authority_reason`, `retry_count`, `max_retries`, `retry_after_at`, `terminal_reason`, and liveness `policy_version`.

## 8. Planner Reactivation Mechanism

`upsert_source_window_feature_authority()` calls `reactivate_planner_for_feature_authority()` when a fresh authority row is written. Reactivation is guarded by exact tenant/model/version/window/`source_snapshot_hash`, updates the build request to `authority_completed`, marks waiting dirty rows `authority_retry_ready`, and inserts a pending planner dirty marker for the same snapshot hash.

## 9. Idempotency Proof

- Build request PK prevents duplicate build intent for the same snapshot.
- Reactivation only transitions requests whose status is one of `authority_build_requested`, `authority_waiting`, or `authority_retry_ready`.
- Duplicate authority completion after `authority_completed` affects zero requests and inserts no second pending dirty marker.
- Existing P3 fit-claim/outbox idempotency remains the only dispatch path.

## 10. `source_snapshot_hash` Scoping Proof

Every request, completion, retry-ready update, and inserted dirty reactivation marker includes exact `source_snapshot_hash`. No window-only or latest-authority retry path is used.

## 11. P3 Lock Compatibility Proof

`lease_debounced_dirty_candidates()` now leases `pending` and `authority_retry_ready` rows through the same SKIP LOCKED planner path. Reactivated candidates still acquire the P4 preflight lease before P2/P4 work and the P3 active execution claim before dispatch.

## 12. No-Dispatch-Before-Fresh-Authority Proof

Authority-yield returns `PlannedFitIntent(... claim=None, fallback_only=False, authority_yield=...)`. It does not call `claim_fit_for_snapshot()` and does not create `b24_fit_dispatch_outbox` rows. Dispatch remains reachable only after fresh authority passes P4 resource/graph checks.

## 13. Retry Budget / Timeout Proof

The request table stores `retry_count`, `retry_after_at`, and `max_retries`. `request_feature_authority_build()` increments retry count on repeated unavailable authority and returns terminal `authority_timeout` with `cardinality_authority_timeout` once the retry budget is exhausted. `mark_feature_authority_build_failed()` records explicit build failure.

## 14. Terminal Authority Failure Taxonomy

New durable terminal reasons:

- `cardinality_authority_timeout`
- `cardinality_authority_build_failed`

These are distinct from `fallback_only`, insufficient data, sparse privacy, feature width, graph complexity, and memory-bound failures.
