## 9-12. Preflight, Transaction, Ordering, Privacy

`run_eligibility_preflight()` executes aggregate SQL only: counts by source, distinct source/channel counts, conversion/revenue counts, confirmed match counts, per-currency sums/observations, min/max timestamps, excluded counts, and density. It does not call source streaming.

`compute_source_snapshot_hash()` opens `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY`, binds `app.current_tenant_id`, runs preflight, and only streams rows when eligible. All writes occur separately through repository fallback upsert.

Every source stream has deterministic `ORDER BY tenant_id ASC, <timestamp> ASC NULLS LAST, id ASC`.

Sparse privacy thresholds block row-level hashing for insufficient cohorts before streaming.

## 13-15. Sentinel, Debounce, Streaming

Sentinel formula:

```text
B24_SOURCE_SNAPSHOT_SENTINEL|source_contract_version=b24-source-v1|eligibility_policy_version=b24-eligibility-v1|fallback_reason=<reason>
```

Example for `insufficient_data`:

```text
173accd3cedc335a07ed0e6ed014b12a261e2fae89a09900e29c96db9d0a5bcc
```

Fallback persistence uses the P1 uniqueness key and `ON CONFLICT DO UPDATE`, clearing compute/artifact fields. Eligible hashing uses `hashlib.sha256().update(canonical_chunk)` over `session.stream(...)` chunks.

## 16-21. Behavioral Proofs

- Replay determinism: canonical JSON uses sorted keys, explicit null representation, UTC timestamp normalization, ASCII JSON, and stable chunk framing.
- Source drift: included amount/status/timestamp changes alter canonical bytes and therefore hashes.
- Exclusion stability: excluded pending/out-of-window noise remains in aggregate excluded counts but does not enter source chunks.
- Tenant/RLS boundary: reads require `app.current_tenant_id`; source SQL filters tenant and `_assert_tenant_guc` fails closed.
- Cold-start/refit-lock separation: fallback rows set `last_eligibility_check_at` but leave `sampling_started_at`, `last_fit_at`, runtime, diagnostics, samples, and artifact fields null.
- Privacy/no-PII: P2 validator rejects identity-table sources, email/IP/raw payload fields, and direct identity queries.
