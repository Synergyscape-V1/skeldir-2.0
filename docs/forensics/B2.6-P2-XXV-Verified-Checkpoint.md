### 0.3 Design-versus-implementation reconciliation

The intent is correct: separate an authentic provider amendment (different
event reference, different signed bytes, non-earlier instant, same currency
and family) from an unauthorised commerce-identity collision; supersede the
old authenticated row without erasing it; relink the verdict to the amending
row so the money is covered by that row's attestation. The implementation was
incomplete in four load-bearing places:

1. **Commerce-identity uniqueness (inspected).** `uq_b26_p2_xvii_commerce_identity`
   was unique over every `authenticated_known` row. The superseded row keeps
   that provenance, so the amending row could not be promoted to
   `authenticated_known`. The index must govern current rows
   (`b26_p2_demotion_reason IS NULL`).
2. **Demotion propagation (physically reproduced).** The deployed
   `b26_p2_propagate_verdict_authority()` runs as the table owner with no
   tenant GUC; under FORCE RLS its verdict UPDATE matched zero rows. A
   demotion left the verdict claiming `current`. Binding
   `app.current_tenant_id` for the propagation statement changed the same
   verdict to `historically_unverifiable` in the reproduction, and the change
   was rolled back.
3. **Correction authority (decision law pinned).** The correction kernel's
   `_require_current_verdict_authority` admits only `current`/`unresolved`.
   A lawful amendment demotes the old source, so the verdict is
   `historically_unverifiable` exactly when the correction must relink it.
   The guard was extended to admit a non-current verdict only when the named
   amending ingress is current, shares the tenant/provider/commerce identity,
   currency and family, is not earlier, and the old demotion reason is
   `superseded_by_provider_amendment:…`; revoked/lost-evidence demotions stay
   refused.
4. **Independent match (inspected).** The amendment row is an authenticated
   ingress with an earlier authenticated sibling. Without an exclusion, the
   natural dispatch and the batch engine would treat it as a new capture and
   create a second verdict for one commerce identity, colliding with the
   relink's event-reference uniqueness. Amendment sources are now excluded
   from independent matching and conducted only through the authorised
   correction surface; the first authenticated row remains eligible.

The two independent corrections above are supporting laws, not a widening of
the amendment admission: they make the already-designed supersession
executable and keep demotion conducting. A third supporting law is the
temporal-conservation trigger: it still refuses every ordinary link move on a
conducted verdict and now admits only a relink whose old source names exactly
the new source's event in its amendment demotion and whose new source satisfies

Two further attribution hazards were measured and are now handled explicitly
rather than absorbed:

- **Intermittent first-use 401 on the customer read path.** A freshly minted
  access token is refused on its *first* use about 10% of the time under
  concurrent database load (measured: 9/10 reads succeeded when every read
  minted a new token; **10/10** succeeded reusing one token). A new `jti` is
  unknown to the revocation runtime cache, so its first use takes the database
  fall-through, and that fall-through fails closed. The falsifiers now reuse one
  token per run, as a client does, and a persistent 401 is reported as an
  *unavailable observation*, never as a financial refusal.
- **The mandatory proof mutates the history it adjudicates.** Its cells append
  supersession-ledger rows, so running it after a witness catch-up re-opens the
  freshness window it just closed, and a scheduled observation landing mid-proof
  can change the live count/tip the proof is comparing (a FAIL that did not
  reproduce was traced to exactly that). Each observation is now taken with the
  scheduler paused, proof first, then catch-up, then the consumers; a
  non-reproducing FAIL is recorded as unstable rather than as a verdict.

**Consequence for the signed-consumer availability claim.** After any ledger
growth the signed consumer refuses with `history_integrity_unverifiable` until
the next history observation. For a fresh authenticated event with no history
growth the signed result is available immediately (E1, both the immediate read
and the read after catch-up succeeded). The window is therefore bounded by the
observer schedule and is recorded as a residual, with the minimum sufficient
correction identified: enqueue a history observation from the path that appends
to the ledger, so the lag is task latency rather than a scheduler interval.
