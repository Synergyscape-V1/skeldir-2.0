## 12. Primary-Key Strategy

Chosen strategy: existing UUID primary-key convention retained with `gen_random_uuid()`.

Rationale: the repo consistently uses UUID tenant/domain identifiers and existing FK/test fixtures expect UUID compatibility. P1 tables are internal authority tables with tenant-scoped composite lookup indexes; no public opaque ID change is needed. Insert locality is weaker than ordered UUIDv7/BIGINT identity, but P1 avoids a cross-repo ID strategy migration. If volume grows, mitigation is to add time/tenant partitioning, lower B-tree fillfactor on append-heavy indexes, or introduce an ordered internal physical key in a dedicated migration while preserving UUID external references.

## 13. Evolvable State Strategy

B2.4 statuses and reasons use `VARCHAR(n)` plus CHECK constraints. No native PostgreSQL enum type is introduced. Future B2.4 phases can alter CHECK constraints through normal migrations rather than enum removal/reordering surgery.

## 14. Alembic Transaction Safety

All indexes on new empty B2.4 tables use regular `op.create_index`. There is no `CREATE INDEX CONCURRENTLY`, no `postgresql_concurrently=True`, and no native enum DDL. The P1 validator rejects concurrent indexes in the transactional migration and rejects native enum DDL.

## 15. Migration Lock Safety

- `CREATE TABLE`: affects only new B2.4 tables.
- `ADD FOREIGN KEY`: locks new B2.4 tables and referenced `tenants`; no existing deterministic ingress/B2.3 tables are altered.
- `CREATE INDEX`: regular transactional indexes on newly created empty B2.4 tables.
- `ENABLE/FORCE ROW LEVEL SECURITY`: applied only to new B2.4 tables.
- `ALTER TABLE ADD CONSTRAINT`: applied during new table creation.
- `VALIDATE CONSTRAINT`: not needed because constraints are created with new empty tables.
- Native enum DDL: not used.

No blocking DDL is added to deterministic ingress or B2.3 hot tables.
