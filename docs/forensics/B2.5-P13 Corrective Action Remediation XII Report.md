## 2. Pre-remediation falsifier and root cause

Two isolated PostgreSQL 15 databases were migrated from the exact starting
main and the candidate branch. Against the starting database, ordinary
principals manufactured global authority using transaction-local custom GUCs:

```text
app_worker, tenant A, app.b24_recovery_reconciler=on
  foreign dispatch SELECT -> 2 visible foreign-capable rows
  foreign dispatch UPDATE -> UPDATE 1

app_worker, tenant A, app.b24_dispatch_claim_access=on
  foreign dispatch SELECT -> 2 visible foreign-capable rows
  foreign dispatch UPDATE -> UPDATE 1

app_worker, tenant A, app.b24_fit_resolution_id=<tenant-B-fit>
  foreign fit SELECT -> 1

app_user
  direct SELECT and INSERT grants on b24_worker_process_authority -> present
```

The effective cause was compositional. PostgreSQL combines permissive RLS
policies with OR. A correct tenant predicate therefore did not constrain a
sibling policy whose complete predicate was a caller-writable setting. The GUC
was context syntactically and authority semantically; no independently
authenticated principal or unforgeable capability stood between the two.

The class inventory found seven consequence-bearing privileged-GUC policies:

1. dispatch claim-capability `SELECT`;
2. dispatch claim-capability `UPDATE`;
3. dispatch claim-function global access;
4. recovery dispatch `SELECT`;
5. recovery dispatch `UPDATE`;
6. recovery-outbox `ALL`;
7. worker-process-authority function access.

The fit parent and all 16 fit partitions separately OR'd tenant identity with
knowledge of `app.b24_fit_resolution_id`. Dormant claim-digest columns reduced
current exploitability of two policies but did not make the authority design
valid.

## 3. Remediation: authority is authenticated and bounded

Revision `202608261200` removes every privileged-GUC policy from the effective
schema and replaces the behavior with three distinct mechanisms:

- fit rows are tenant-only at the parent and every partition; resolution SQL
  binds both `tenant_id` and `fit_id`;
- global publisher access remains tied to the independent
  `app_dispatch_publisher` login established by C11;
- worker-global operations execute only inside narrowly granted
  `SECURITY DEFINER` state-machine functions. Their internal RLS policies require
  both `current_user = migration_owner` and `session_user = app_worker`, a
  conjunction an ordinary direct SQL session cannot manufacture.

The new recovery functions only lease bounded due rows, mark one identified
publishing row successful, or mark one identified publishing row failed. They
validate row identity and state, cap batch/timeout/attempt/error inputs, have a
fixed search path, revoke `PUBLIC`, and grant execution only to `app_worker`.
The successful recovery transition updates the recovery and dispatch rows in
one database transaction; the prior application implementation performed two
separate statements.

All direct table privileges on `b24_worker_process_authority` are revoked from
ordinary roles. Existing register/query behavior remains reachable only through
the already bounded process-authority functions.

## 8. Open-world search

Several new hypotheses were generated from seams rather than auditor wording:

- **Recovery transition atomicity**: moving authority into a bounded function
  exposed that application success previously updated recovery then dispatch in
  separate statements. Closed by one transactional function with strict source
  states.
- **Inherited validators could require the vulnerability**: the P6 and P9
  source gates asserted the presence of fit-resolution and recovery GUCs. They
  were updated to assert tenant-bound resolution and bounded database functions,
  with their own negative controls preserved.
- **Execution-artifact identity could preserve the vulnerable-era assertion**:
  P11 still required the old P6 test whose name asserted fit ID was an explicit
  RLS capability. The first candidate CI pass made every P6 runtime test green
  and then correctly rejected the stale JUnit identity. The governed manifest
  now requires the replacement tenant-bound, non-capability assertion.
- **A required aggregator could hide dependency failure by skipping**: closed
  with `if: always()` plus explicit equality-to-`success` for every dependency.
- **Pooled residue could remain an application security boundary**: direct
  residue and a second-backend experiment establish that database policy does
  not depend on cleanup; the Bayesian engine remains `NullPool` as defense in
  depth.
- **A global-recovery proof could accidentally test database cleanliness**: a
  deliberately dirty local database showed that assuming the new witness was in
  the first global batch was invalid. The test now orders its own due dispatch
  and recovery witness explicitly, so it proves the transition while preserving
  unrelated backlog.
- **Dormant capability columns could be mistaken for live security**: the
  claim-digest policies are removed. Compatibility columns remain data only and
  confer no policy authority.
