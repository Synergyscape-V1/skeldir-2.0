## 2. Root cause

Corrective V moved every *value* in B2.8 from assertion to derivation. It left two
*events* self-asserted and one compatibility predicate measuring the wrong property.

### 2.1 A request proved a writer, not a requester

`b28_enforce_request_consequence` establishes that `requested_by_credential_id` names a
live credential row in the right tenant, that its `agent_clients` parent is live, and
that `requested_by` is the derivation of the client id. Every one of those facts is
readable from the credential *row*. None requires the writer to hold the credential's
plaintext secret.

The application half authenticated honestly — prefix lookup, `hmac.compare_digest`,
revocation, status, expiry, tenant — and its conclusion left no durable trace. So the
two universes Directive VI names H-DU-VI-01 produced byte-identical rows:

```text
present token → verify → insert request        (library path)
know credential row id → insert request        (dedicated-role SQL)
```

The durable layer is the layer the phase claims as its trust root, and at that layer the
possession proposition was simply absent.

### 2.2 A result asserted an execution count it could not witness

`solver_invocations integer NOT NULL` reads as *the governed solver ran this many
times*. Corrective V narrowed the claim in prose — what the database proves is
extensional, that the persisted allocation IS the value of `b28_recompute_allocation`
over the request's retained evidence — but the persisted vocabulary was never changed to
say so, and no column carried a comment at all. An independently recomputed allocation
carrying `solver_invocations = 1` was therefore accepted.

### 2.3 Readiness confused a known revision with a compatible one

`assert_production_construction_authority` accepted any revision found anywhere under
`alembic/versions/**`. This is the anti-corroboration trap Directive VI names verbatim:

```text
revision is somewhere in repository history → ready      (measured familiarity)
revision is explicitly compatible with this build → ready (the required law)
```

A second, quieter defect sat underneath it. The revision scanner used
`^revision\s*=\s*["']…`, which matches a *bare* assignment. 132 of the repository's 171
migration modules declare `revision: str = "…"`, so the "every revision this repository
knows" set was in fact an arbitrary 39-member subset. That direction was fail-closed and
therefore harmless, but a predicate whose domain is accidental cannot be reasoned about.

### 2.4 The custody boundary was a wish, not a measurement

`consequence_custody.py` claimed "a credential that only one code path can reach is a
credential the rest of the process cannot spend". `_assert_permitted_caller` fences the
*helper*. The DSN lives in the process environment and `psycopg2.connect` is importable
from anywhere, so the audit refuted the claim in four lines.

## 3. The repair

### 3.1 Possession becomes a durable, single-use, request-bound witness

`b28_request_authentications` records one fact: *at this instant, a caller proved
possession of this credential's plaintext secret, for this exact request*.

**No principal holds INSERT on it.** Measured live across all ten runtime logins:

```text
relation                       role                     S I U D
b28_request_authentications    app_user                 1 0 0 0
b28_request_authentications    app_ro                   1 0 0 0
b28_request_authentications    app_worker               1 0 0 0
b28_request_authentications    app_rw                   0 0 0 0
b28_request_authentications    app_b28_requester        1 0 0 0
b28_request_authentications    app_b28_solver           0 0 0 0
b28_request_authentications    app_trust_issuer         0 0 0 0
b28_request_authentications    app_trust_signer         0 0 0 0
b28_request_authentications    app_dispatch_publisher   0 0 0 0
b28_request_authentications    app_celery_transport     0 0 0 0
```

The sole writer is `b28_authenticate_request_possession`, measured from the catalog as:

```text
owner       migration_owner
prosecdef   true                     (SECURITY DEFINER)
proconfig   search_path=pg_catalog, public
EXECUTE     app_b28_requester=true; every other runtime role=false
```

It takes the plaintext token, recomputes `encode(sha256(convert_to(token,'UTF8')),'hex')`
and compares it to the stored `token_hash`; re-checks revocation, status, `revoked_at`,
`expires_at` at the *database's* clock, client liveness and tenant; derives the request
binding itself; and returns the witness id. The caller cannot name the client or the
credential — both are read out of the row the secret resolves to. A wrong prefix and a
wrong secret produce the same refusal on purpose, so a caller cannot learn which prefixes
exist.

The request then names that witness through a `NOT NULL` foreign key with a `UNIQUE`
index:

```text
CREATE UNIQUE INDEX uq_b28_request_authentication
  ON public.b28_simulation_requests USING btree (request_authentication_id)
```

Three properties follow, and they rest on different mechanisms so no single change
removes them all:

* a request without a witness is not representable — no grant, trigger or policy is
  involved, the column simply cannot be filled;
* a witness minted for one request cannot authorise another — `b28_enforce_request_possession`
  re-derives the binding from the row being inserted and requires equality, rather than
  comparing a stored copy;
* a witness cannot be replayed — the unique index refuses the second request.

The binding is an ordinary `IMMUTABLE` function over `(tenant_id, request_ref,
source_issuance_envelope_hash, input_snapshot_hash)`, `EXECUTE` granted to `PUBLIC`, so
an auditor holding only `SELECT` can recompute the possession binding independently and
check it against the stored row without trusting the writer.

### 3.2 The persisted solver contract states the proposition the system proves

Directive VI §18 offers two architectures. **Architecture B (extensional)** is chosen,
because it is what the product needs and what the database can verify: the allocation
must be right; which process computed it is not a fact anyone consumes, and an execution
witness produced and verified by the same authority would be self-certification
(Directive V H-RC-V-08).

```text
DROPPED  b28_simulation_results.solver_invocations
ADDED    b28_simulation_results.solver_consequence_kind text NOT NULL
         CHECK (solver_consequence_kind = 'governed_deterministic_consequence')
```

with the column's own comment stating both halves of its meaning:

> DERIVED VALUE. asserts exactly this and nothing more: allocations is the value of
> b28_recompute_allocation over the request's retained evidence, verified inside this
> trigger. It is NOT a claim that any particular process executed a solver — no execution
> witness exists and none is claimed (Directive VI section 18, Architecture B).

The in-process counter survives in `SimulationResult.solver_invocations` because *there*
it is an honest observation: it is what makes "a refusal ran no solver" a measurement
rather than an inference, and the container parity probe still reads it as `0`. It is no
longer persisted.

## 9. Gate R — full compositional conduction, and the limit the system actually has

Directive VI §29 requires one fresh state to conduct from authenticated raw commerce

`n_samples_actual ≥ 1600`, `r_hat_max ≤ 1.01`, `ess_min ≥ 400`, `divergence_count = 0`) →
confidence projection → remote-signer signature verified from the public JWKS → durable
issuance.

**This remediation carries that exact state across the P14 boundary**, inside the

```text
read_only source Trust
  → b28_request_policy_forbids:read_only
  → durable requests 0, results 0, proposals 0, possession witnesses 0
```

Measured independently on the fresh cluster to confirm the mechanism:

```text
policy_state=read_only        REFUSED b28_request_policy_forbids:read_only
                              durable_requests_for_this_trust=0
                              possession_witnesses_for_tenant=0
policy_state=simulation_only  CONDUCTED result_id=7c9478d7-… proposal_id=5fdb08fd-…
                              durable_requests_for_this_trust=1
                              possession_witnesses_for_tenant=1
```

Two things follow.

**The conservation law holds on physically conducted state.** `Authority(downstream) ≤
Authority(source Trust)` is not an argument about code; it is the observed behaviour of
the deployed topology on a Trust that came out of a real posterior. And the refusal earns
*nothing*: not a result, not a proposal, and not even the possession witness — because the
witness is minted inside the request transaction that rolls back. There is no orphan proof
that somebody asked for something that never happened. That is Directive VI §23's temporal
property, obtained structurally rather than by cleanup.

**Declared limitation.** `read_only_policy_authority()` in
`backend/app/trust/policy_defaults.py` is the only producer of `policy_action_authority`
in the tree, and `read_only` is strictly weaker than simulating. A fully conducted Trust
therefore *cannot* admit a B2.8 simulation, and P14 correctly refuses it. The durable
request → result → proposal legs are consequently provable only over a Trust whose policy
authority is supplied outside the conducted path — which the R4/R5/R6 suites do with real
Ed25519 signing through the P5/P8 path and real issuance under the production principals.

The seam is exactly one field wide, it is named, and it is a product-sequencing fact
rather than a P14 defect: no tenant-level Trust policy-configuration surface exists yet
(the schema carries no policy relation; `b24_inference_policy_registry` and
`b24_fit_policy_replan_lineage` are B2.4 sampling policy, unrelated). Closing it requires
a policy-authority surface that can issue `simulation_only` for a design-partner tenant,
at which point the C19 leg's `CONDUCTED` branch — already written and already asserted —
becomes the live path with no further P14 change.

This is recorded rather than smoothed. Under Directive VI §34 an independent auditor may
reasonably classify Gate R as closed-with-limitation or as still open; engineering's
position is that the gate is driven, the law is observed on conducted state, and the
remaining segment is blocked by an absent product surface rather than by anything P14
does or does not prove.

## 10. Open-world hypotheses (Directive VI §35)

Ranked by consequence. The top two were behaviourally investigated.

**OW-VI-1 — The platform cannot issue a Trust that admits simulation (action authority;
HIGHEST).** TESTED, CONFIRMED, DECLARED. `read_only_policy_authority()` is the only
producer of `policy_action_authority`; grep over the tree finds no other. Measured end to
end: a conducted Trust is refused at the durable layer by name. Consequence: B2.8's
entire durable path is unreachable from production ingress today. This is the finding
that shapes §9 and it was not stated in any prior report.

**OW-VI-2 — `known_revisions()` measured 39 of 171 modules (schema compatibility;
HIGH).** TESTED, CONFIRMED, FIXED. The regex required a bare `revision =` assignment;
132 modules use `revision: str = …`. The direction was fail-closed, so no database became
*more* acceptable, but the "unknown revision" refusal was firing for revisions the
repository does know — a misleading diagnosis — and the predicate's domain was accidental.
AST parsing scoped to `version_locations` now yields 170 and one head.

**OW-VI-3 — A UTF-8 BOM made one migration module invisible to AST parsing (schema
compatibility; MEDIUM).** OBSERVED, FIXED. `202607191200_b25_p9_machine_identity.py`
carries a BOM; `ast.parse` refuses a source string starting with one, so the module was
silently skipped and its parent became a phantom second head. Read as `utf-8-sig`. Any
future tooling that AST-parses migrations inherits this trap.

**OW-VI-4 — `alembic/versions/005_webhook_secrets` is outside `version_locations`
(migration hygiene; MEDIUM).** OBSERVED, CONTAINED. It holds revision `202511171000`,
which Alembic never loads. A head computation that scanned the whole tree would report it
as a second head and make a linear chain look divergent. `_chain_directories()` reads
`alembic.ini` so the head computation agrees with the tool that applies the migrations.
The orphan file itself is untouched and remains latent debt.

**OW-VI-5 — Trigger firing order is a diagnostic dependency (request authority; LOW).**
OBSERVED, PINNED. PostgreSQL fires BEFORE triggers in name order, so
`trg_b28_request_consequence` precedes `trg_b28_request_possession`. Both must pass, so
order is never a security property — but three existing probes assert on the consequence
guard's specific reason codes, which would change if the order flipped. A test now pins
it and the migration says why.

**OW-VI-6 — The witness relation grows without bound (operational; LOW).** OBSERVED,
UNFIXED. A minted-but-unused witness is never collected. It leaks nothing (it names no
secret) and the volume is one row per lawful request plus abandoned attempts, but a
retention policy belongs in the same phase that gives requests one. Recorded as debt.

**OW-VI-7 — `migration_owner` inherits the runtime roles (privilege hygiene; LOW).**
CONFIRMED, unchanged from audit 72's OW-A6. Owner-compromise implies runtime
impersonation for free. Contained — the owner can already drop every guard — and out of
scope here, but the direction is worth keeping on the register.
