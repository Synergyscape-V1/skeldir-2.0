# B2.5-P13 XVI CHECK Constraint NULL Semantics Survey

* Date: 2026-08-30
* Scope: every PostgreSQL `CHECK` constraint in schema `public` at the
  protected-main XV head and at Corrective XVI head

Governing question: can a nullable operand make a predicate that advertises a
required property evaluate to SQL `UNKNOWN`, which PostgreSQL accepts?

## Method

The survey was executed against PostgreSQL 15 after replaying the repository's
real Alembic chain as the non-superuser, non-`BYPASSRLS` `migration_owner`.
For every `pg_constraint.contype = 'c'` row in `public`, it joined the target
relation's nullable `pg_attribute` rows, detected identifier-bound references
with PostgreSQL's `\m` / `\M` word boundaries, and classified the reference as
explicit only when the predicate also stated `column IS NULL` or
`column IS NOT NULL`. Partition copies were retained in the physical count and
collapsed by `(constraint_name, nullable_operand)` for semantic disposition.

This is a candidate generator, not a proof by itself. Each unique candidate was
then read with its sibling constraints and directly exercised where NULL could
change the advertised truth. Corrective XVI's live test reruns the complete
catalog query and fails unless the candidate set is empty.

## Baseline result and disposition ledger

The protected-main baseline contained 1248 physical `CHECK` rows. Partition
copies produced 610 candidate references, collapsing to seven unique semantic
shapes.

| Constraint and nullable operand | Baseline disposition | Corrective XVI disposition |
|---|---|---|
| `ck_trust_access_log_issued_requires_crypto` / `issued_signature_hash` | `VALIDATED DEFECT`: a fabricated non-NULL hash was accepted without signature evidence, and a NULL hash made the whole issued arm `UNKNOWN` and was also accepted | New `issued` rows require a non-NULL 64-byte raw Ed25519 signature, its non-NULL SHA-256 hash, key id, attempt time, issued time, and envelope hash; both adversarial writes are refused as ordinary `app_user` |
| `ck_bayesian_model_fits_available_interval_requires_passed_diagnostics` / `divergence_count` | `VALIDATED DEFECT`: `credible_interval_status='available'` with NULL divergences could satisfy the advertised passed-diagnostics guard through `UNKNOWN` | Predicate now states `divergence_count IS NOT NULL AND divergence_count = 0`; the direct NULL mutation is refused |
| `ck_bayesian_model_fits_available_confidence_complete` / `confidence_bucket` | NULL is the intentional unclassified state, but the intent was implicit in this constraint | Predicate now begins with the explicit harmless arm `confidence_bucket IS NULL` |
| `ck_bayesian_model_fits_available_confidence_complete` / `confidence_bucket_reason` | A sibling classification-state constraint rejects a classified bucket with no reason, but this predicate's completeness claim was implicit | Classified confidence now explicitly requires `confidence_bucket_reason IS NOT NULL` before matching the governed bucket/reason pair |
| `ck_bayesian_model_fits_available_confidence_complete` / `confidence_evidence_snapshot_hash` | `VALIDATED DEFECT`: when the entire evidence tuple was NULL, the sibling tuple constraint allowed its intentional empty arm and this completeness predicate evaluated to `UNKNOWN`; a low/medium/high classification could therefore lack evidence | Classified confidence now explicitly requires a non-NULL evidence hash equal to `source_snapshot_hash`; the production terminalization with an all-NULL evidence tuple is refused |
| `ck_b24_fit_dispatch_outbox_claim_capability_digest_sha256` / `claim_capability_digest` | NULL is intentional before a claim capability has been minted | Predicate rewritten as the explicit safe idiom `claim_capability_digest IS NULL OR ...` |
| `explanation_cache_cache_hit_count_check` / `cache_hit_count` | NULL is an intentional legacy/unmeasured value | Predicate rewritten as the explicit safe idiom `cache_hit_count IS NULL OR cache_hit_count >= 0` |

No candidate was waived on narrative alone. The two intentionally nullable
single-column constraints were rewritten to state that policy. The classified-
confidence predicate was made self-contained even where a sibling constraint
already supplied a backstop.

## Corrected-head result

After migration `202608301200`, the live catalog contained 1251 physical
`CHECK` rows and 307 unique names. It produced 1350 nullable-column references
before intent filtering and exactly zero implicit candidates afterward:

```text
c16_nullable_check_candidates=0
c16_nullable_check_mutations_refused=2
```

The two non-Trust direct mutations are:

1. terminalize a classified confidence with its complete evidence tuple NULL;
2. set `divergence_count=NULL` while the interval remains `available`.

Both raise their named database constraints. The Trust-specific live test adds
three more refusals as ordinary `app_user`: hash-only completion, NULL-hash
completion, and a runtime transition into the migration-only `issued_legacy`
state.

## Reproduction

The merge-governing command is:

```bash
SKELDIR_B25_P13_C16_DB_PROOF=1 \
SKELDIR_B25_P13_E2E_PROOF=1 \
python -m pytest \
  backend/tests/trust/test_b25_p13_c16_bidirectional_issuance_truth.py \
  -q -s --no-header
```

The database must first be provisioned by
`.github/actions/setup-postgres-ci/action.yml` and migrated to `202608301200`.
The required C16 job performs that provisioning, a downgrade/upgrade round
trip, the complete catalog survey, and the direct mutations. The query and its
zero-candidate assertion live in the test rather than this document, so editing
this narrative cannot make the gate green.

## Boundary

This survey covers PostgreSQL `CHECK` constraints in `public`. It does not claim
that arbitrary trigger functions, application predicates, or constraints in an
extension-owned schema are free from unrelated NULL errors. Those are different
mechanisms and require their own inventories.
