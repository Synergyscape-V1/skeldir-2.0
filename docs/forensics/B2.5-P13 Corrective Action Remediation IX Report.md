## 1. What the audits said, and what was true

Corrective Action VIII connected the chain. Both auditors credited that and both
rejected completion, for the same reason stated two ways: **a chain that
conducts is not yet a chain that stays truthful when reality is messy.**

Three of their findings were already in my own C8 report as open items. One was
not, and it was mine:

> The feature-authority producer derives the source hash and the P2 preflight
> from one PostgreSQL snapshot, and provider and campaign cardinality from a
> later transaction, yet persists all of it under the first snapshot's hash as
> `fresh`.

My C8 report had claimed the opposite in plain words — "the producer recomputes
the source hash inside one repeatable-read transaction and writes only when the
hash it observes is the hash the request named." The hash and the preflight were
in that transaction. Provider and campaign width were not. The sentence was true
about half the row and I wrote it as though it were true about all of it.

The test I shipped alongside it could not catch the difference. It compared the
caller's expected hash against a value the *first* transaction had already
returned, and that comparison is structurally blind to anything happening after
it. A guard that runs before the gap cannot see into the gap.

## 3. Remediations

### F-08 — one snapshot, five measurements

The producer now measures the hash, the P2 preflight (which supplies channel and
currency width) and both walked dimensions **inside one
`REPEATABLE READ READ ONLY` transaction**. `compute_source_snapshot_hash` gained
one optional parameter, `within_snapshot`, which runs an additional measurement
inside the transaction it already holds and carries the result back on the
result object. Every existing caller is unaffected.

The point is not that the producer now *detects* a mid-flight mutation. It is
that under one snapshot there is nothing to detect: a commit made after the
transaction begins is not visible to any read within it, so the five
measurements agree because they are one observation.

**The proof stands in the old defect's window and pushes.** A real settlement —
introducing a provider and a campaign that exist in no earlier state — is
committed from a *separate connection* at exactly the moment the old code was
between transactions. The measurement must not see it.

Reintroducing the split makes it fail with the hybrid row itself:

```
provider_count            2  (S1)   expected 1  (S0)
campaign_or_feature_count 7  (S1)   expected 6  (S0)
hash                      S0
```

That is the row Audit 44 described, produced on demand.

### F-05b — a narrow door for planner-owned degradation

The dispatch fence has always admitted two planner-authored states without
dispatch authority — `queued` and `pending` — because scheduling a fit is not
the same act as producing one. Declaring that a fit *cannot* happen belongs to
the same category and was simply missing from the list.

The state is added narrowly. It is admitted only for a row carrying **no
computational consequence whatsoever**: no artifact, no artifact hash, no
confidence evidence hash, no sampling/fit/completion timestamps, no runtime, no
sample or chain count, no r-hat, no ESS, no divergences, no credible interval,
and a confidence bucket that is explicitly `unavailable`.

Three forgeries were attempted directly against the database and all three were
refused:

| Forged row | Result |
|-----------|--------|
| `fallback_only` carrying an artifact | `b24_dispatch_fence_rejected` |
| `fallback_only` carrying `available` confidence | `b24_dispatch_fence_rejected` |
| `fallback_only` carrying sampling evidence | `b24_dispatch_fence_rejected` |
| the planner's genuine no-compute declaration | persisted, 0 dispatch rows |

The forgery boundary underneath the trigger is the table grant, and it is
stronger than the trigger: `app_user` — the API runtime role — holds **SELECT
only** on `bayesian_model_fits`. Nothing reachable from an HTTP request can write
a fit row of any shape.

### F-07 — failure isolation without losing the failure

Containment is per-tenant, and the disposal in `finally` still runs, so C7's
residual-authority logic decides what happens to the failed obligation rather
than this loop discarding it. `Exception` and not `BaseException`, deliberately:
a hard worker time limit is not a per-tenant fault and must keep propagating.
What was contained is reported in the task result — `failed_tenant_count` and
`failure_classes` — because a planner that silently absorbed exceptions would
trade one invisible defect for another.

Two properties are proven, and the second does not follow from the first:

- **containment** — a failing tenant does not prevent its batch-mates from being
  planned in the same pass;
- **bounded progress** — a tenant that fails on *every* pass, seeded oldest so it
  is leased first every time, still does not prevent healthy tenants from
  progressing across four consecutive cycles.

### F-10 — impossible work stops being work

A request naming a snapshot that has been superseded is not unavailable, it is
historically impossible, and no horizon resolves it. The bounded-retry columns
for exactly this were already on the table and never consulted — `retry_count`,
`max_retries`, `terminal_reason`, `terminal_at` — and the dirty-event vocabulary
already contained `authority_retry_superseded`. The pieces were present and
unconnected, which is what Audit 44 predicted.

Past its own retry horizon the request terminates as `authority_superseded`, the
schedule is cleared, and the dirty evidence waiting on it is released. A request
naming the snapshot that *does* exist still completes on its first cycle and is
charged no retry — otherwise this would have traded infinite retry for silent
starvation.

### F-09 — every fit was granted a budget of zero samples

The fit-claim INSERT hard-coded its execution budget: `max_runtime_seconds 60`,
`max_samples 0`, `max_cores 1`. The sampler refuses any fit whose sample budget
is below what the sampling policy intends to draw, and zero is below every
policy there could be.

**So every fit the planner has ever claimed was structurally unexecutable.** The
worker authenticated, took its lease, loaded the row, and refused it
`policy_rejected` before compute started.

Nothing caught it because the only proof that a fit can execute writes its own
fit row, with its own budget, and never asks the planner for one — the same
fixture substitution that hid F-06, one layer further down. The budget is now
read from the policy that spends it.

## 4. F-11 — the incompatibility, and how it was resolved

Building C9-J revealed something neither audit found and no component was
individually wrong about. Three governed, separately versioned policies — the
B2.4-P5 runtime cage, the P6 sampling policy and the P7 diagnostic policy — had
never been asked to hold at the same time. Asked together, they were impossible.

It had two arms, and each was independently sufficient.

**Arm one: R-hat could not exist.** The sampler ran inside a single-process cage,
and the cage's own validator required `chains == 1`:

```python
if self.blas_cores != 1 or self.cores != 1 or self.chains != 1:
    raise ValueError("P6 preserves P5 single-process runtime cage")
```

R-hat compares variance *between* chains. With one chain there is nothing to
compare, so it is NaN, and the diagnostics rejected the fit as
`nonfinite_diagnostic` before sample size was considered at all.

**Arm two: ESS could not reach its threshold.**

```
b24-p6-sampling-policy-v1     draws 64 x chains 1  =  64 posterior samples
b24-p7 diagnostic policy      requires effective sample size >= 400
```

Effective sample size tracks the number of draws: usually below it, and modestly
above it when NUTS samples antithetically. An earlier assertion of mine that ESS
"cannot exceed" the draw count was too strong — exact-main CI caught it at 65.66
against 64 draws, and the assertion was corrected rather than the observation
explained away. The substantive point is about magnitude, not a strict bound: a
threshold of 400 against 64 draws is a 6.25x gap that no sampler quality closes.

The consequence was total. **No fit this system could produce was capable of
passing its own diagnostics**, whatever the data. Every real sampled fit was
truthfully reported `nonconverged`, and a usable confidence was unreachable
through the production sampling path.

### 4.1 The finding underneath the finding

F-11 was not an undetected defect. It was a **green check whose passing
condition was the defect.**

The B2.4-P6 real-fit proof is this repository's flagship evidence that the
sampler works. It asserted:

```python
assert row == {
    "status": "succeeded",
    "credible_interval_status": "not_available",
    "diagnostic_status": "failed",
    "diagnostic_failure_reason": "nonfinite_diagnostic",
    "n_samples_actual": 64,
    ...
}
```

The P5 runtime harness pinned the same pair independently: `n_chains == 1` and
`n_samples_actual == 64`.

So the system did not merely fail to notice that no fit could ever converge. It
**asserted that outcome as correct, on every run, and reported success for it.**
Those two proofs were green precisely *because* the pipeline could not produce a
usable confidence. Had either asserted convergence, F-11 would have surfaced the
day the P7 thresholds landed.

This is why the incompatibility survived across phases: the evidence surface was
shaped around it. That is a different and more serious class of defect than a
missing test, and it is recorded here as the primary finding of this corrective.

### 4.2 Why I escalated rather than resolved

I did not resolve F-11 when I found it, and the reason is the one I got wrong in
C8 and was corrected on: **this was a decision with an owner.** Lifting the
single-chain cage touches the P5 process-isolation guarantee. Raising the draw
count spends compute against a governed time limit. Lowering the ESS threshold
weakens a published convergence criterion. The directive is explicit that
governed thresholds may not be moved to make a journey pass, and picking a number
to turn a proof green would have been exactly that.

It was pinned in arithmetic rather than described in prose, so that it would go
red the moment either arm lifted.

### 4.3 The governed resolution

The policy decision supplied for F-11 states the principle directly:

> F-11 is resolved by preserving diagnostic rigor and changing sampling topology,
> not by weakening acceptance thresholds.

That is the correct diagnosis, and it identifies the actual error. The cage was
written as though *one process* meant *one chain*, and those are different
things. PyMC separates them explicitly: `chains` is how many independent Markov
chains exist, `cores` is how many run in parallel. With `cores=1` PyMC samples
the chains **sequentially**, in one process, with one BLAS thread and no
multiprocessing fan-out.

The cage constrains parallelism. It never constrained chain count — which is
visible in the runtime module's own thread-budget arithmetic:

```
worker_concurrency x pymc_cores x blas_total_threads
```

Chains do not appear in that product, because they do not consume a thread.
Requiring `chains == 1` bought no isolation whatsoever and cost the diagnostics
their most important statistic.

**Every acceptance threshold is unchanged:**

| Criterion | Before | After |
|-----------|--------|-------|
| R-hat maximum | ≤ 1.01 | ≤ 1.01 |
| Effective sample size | ≥ 400 | ≥ 400 |
| Divergences | 0 | 0 |
| Execution cores | 1 | 1 |
| BLAS threads | 1 | 1 |
| Chains | 1 | **4, sequential** |
| Draws per chain | 64 | **1000** |
| Tuning per chain | — | **1000** |

### 4.4 The fourth authority

Three policies that must hold together, and nothing responsible for noticing
when they do not, is the shape of the defect rather than an accident of it. So
the remediation adds what was missing: a versioned **inference compatibility
profile** (`b24-inference-profile-v1`) that names one combination and validates
it at import — not four minutes into a run.

It was deliberately **not** implemented by merging P5, P6 and P7 into one version
number. Collapsing them would have hidden the incompatibility rather than
governed it, and would make a signed confidence uninterpretable the moment any
one of them evolved. They stay separately versioned; the profile asserts they are
jointly satisfiable.

The profile refuses six combinations, each of which was some part of F-11:

| Refused | Why |
|---------|-----|
| `chains = 1` while R-hat is required | R-hat does not exist below two chains — the exact F-11 configuration |
| ESS threshold above retained draws | Structurally unreachable, whatever the sampler does |
| Sampler and diagnostics disagreeing on chain count | Two policies drifting while each stays internally consistent |
| `cores > 1` or `blas_cores > 1` | Breaks the P5 cage the resolution preserves |
| Fit budget exceeding its containment boundary | A fit fenced above the envelope that contains it |
| A non-zero divergence tolerance | Softening a threshold this corrective does not touch |

Sampling vocabulary was made explicit at the same time, because it stopped being
obvious the moment `chains` exceeded one. Version 1 had a single `sample_count`
meaning *draws + tune*, per chain, with no chain factor — harmless while there
was exactly one chain and silently wrong afterwards:

```
draws_per_chain          retained posterior draws, per chain
tune_per_chain           tuning iterations, per chain, discarded
posterior_draws_total    chains x draws_per_chain      -> n_samples_actual
total_chain_iterations   chains x (draws + tune)       -> max_samples budget
```

`max_samples` governs `total_chain_iterations` — the whole workload the fit is
authorised to perform, tuning included, because tuning costs the same wall clock
as drawing. `n_samples_actual` reports what was kept. Neither is called
`sample_count` any more.

## 5. C9-J — the journey, now complete

The journey writes **no feature authority, no fit, and no dispatch claim**. One
settlement run, and at each stage exactly what the previous stage produced:

```
real settlements committed
  -> production invalidation trigger writes the dirty evidence
    -> production planner judges it fittable and asks for an authority
      -> production cardinality producer measures the exact snapshot
        -> production planner claims the fit and mints a dispatch lease
          -> production relay leases that row
            -> production worker executes its payload
              -> four sequential chains in one fenced process
                -> real diagnostics on a real posterior
                  -> available confidence, persisted
                    -> production Trust route, signed and JWKS-verified
```

Possession of a dispatch id is **not** authority to execute, and the system said
so: reading the outbox row directly and executing it returns `UNAUTHORIZED` from
the fence. That refusal is how F-09 was found. The row is leased through the
production relay, and the only bridge is the broker hop — proven separately by
the live transport proof.

**C9-J is recorded PASS.** A real financial change becomes a signed, usable
confidence with no test-written authority at any seam. The journey asserts the
resolution rather than merely surviving it: four chains, 4000 retained draws, a
finite R-hat inside 1.01, ESS clearing 400, zero divergences, diagnostics passed
with no failure reason, retained artifact evidence, and a runtime inside the
governed budget. Each goes red if the topology regresses.

Correspondence is asserted in the vocabulary each layer actually speaks. B2.4
classifies a fit into `high`/`medium`/`low` or a refusal; B2.5 translates that
into a bounded `confidence_status` for the envelope. Asserting the bucket string
appears in the envelope would assert the two vocabularies are one, which they are
deliberately not — the B2.5 boundary exists so a B2.4 policy change cannot
silently alter what a signed claim means. My first attempt asserted exactly that
and CI rejected it; the assertion was wrong, not the result.

### 5.1 A constraint that had never been evaluated

Reaching available confidence for the first time reached
`ck_bayesian_model_fits_available_confidence_complete` for the first time. It
governs what a fit must carry to claim a usable bucket — nineteen conjoined
conditions, including `source_read_started_at` and `source_read_completed_at`.

The P6 fixture never set them. The production claim path records both from the
snapshot; the fixture inserted its fit directly and left them NULL, and nothing
noticed for as long as no fit it created ever reached a bucket the constraint
applies to. The fixture now records the window from the same snapshot it already
computes.

This is the same lesson as F-06 and F-08 in a third place: **an integrity control
that has never once been evaluated is not evidence of integrity.** It was
correct, it was live, and it had nothing to say until the pipeline finally
produced the state it governs.

## 8. What is not claimed

- **The posterior is accepted, not endorsed.** Four chains make R-hat computable
  and 1000 draws per chain make ESS reachable; whether any *particular* posterior
  converges stays an empirical question the diagnostics answer at runtime. The
  compatibility profile asserts the policies can be jointly satisfied, never that
  a given fit is good.
- **The model itself is unchanged and is not claimed to be adequate.** It is a
  one-parameter Normal mean. F-11 was about whether the pipeline can express a
  usable confidence at all, not about modelling quality.
- **The 240/270/300-second envelope is not proven to be sufficient for every
  future model.** It is proven sufficient for this one, at 12 seconds. A larger
  model would need the profile revalidated, which is what the profile is for.
- The historical-freshness transition (C9-L) at the *envelope* level, and the
  duplicate-delivery idempotency injections (C9-D), are exercised at the database
  tier by existing C8 proofs but are not assembled as end-to-end journeys here.
