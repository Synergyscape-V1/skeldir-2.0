## E. Root-cause map

Four validated root causes explain all twenty-nine defects.

**RC-XVII-01 — Authority was modelled by possession rather than by provenance of
consequence.** Explains Audit 59's H-XVI-B1, B2, B3, E1, E2 and G. The
remediation is structural, not a further role check: the principal that may
*assert* a cryptographic consequence is now exactly the principal that can
*produce* one, and the database verifies correspondence between the asserted
evidence and the attempt row that carries it. `RC-XVII-02` (history as mutable
row state) and `RC-XVII-03` (enforcement terminating one layer too early) are
sub-cases of the same pattern and are closed by the same change.

**RC-XVII-04 — Recovery was tested as a function rather than as a topology.**
Explains Audit 59 H-XVI-D2 / OW-2 and, in this session, F-8 through F-11: every
one of those defects is a step that had never been executed. The remediation is
a CI step that runs the real control plane, and a working practice of extracting
each CI step from the workflow and executing it locally before pushing.

**RC-XVII-07 — A new responsibility was implemented where it was convenient
rather than where its phase owns it.** Explains F-22, F-23 and F-24: durable
completion legitimately needs public-key adjudication and the API legitimately
needs to reach a separate signer, but both landed inside modules whose phase
locks forbid exactly that. In each case the gate was right and the fix was to
give the new responsibility its own declared home, not to widen the lock.

**RC-XVII-06 — CI co-evolved with the implementation's ontology.** Explains F-1,
F-2, F-3, F-4, F-12, F-13, F-15, F-18, F-19, F-25, F-27 and F-28: assertions
that named the shape the author expected, or the shape the architecture used to
have, rather than the shape the system has. Eleven of the twenty-eight defects
are this one pattern, which is why the remediation is a binding rather than
eleven edits. The remediation adds
cross-artifact bindings (asserted trigger identity ⊂ created trigger identity;
caller inventories for the new signing entry points) so that this class of drift
fails a static gate rather than a live run.

| `signing` | A durable attempt exists; the private key may be entered | issuer |
| `signature_outcome_unknown` | The attempt began; whether a signature exists is genuinely unknowable | issuer (live path or reconciler) |
| `signature_known` | A valid signature **definitely** exists and its exact artifact is durably retained | **signer only** |
| `issued` | The retained artifact was verified against public key authority and projected | issuer, and only from `signature_known` with exact evidence correspondence |
| `issued_pre_xvii` | A pre-XVII completion whose cryptographic correspondence was never consequence-coupled | migration only; terminal |
| `issued_legacy` | A pre-C16 completion with no retained raw signature | terminal |
| `failed` | Abandoned after authorization, before the private key | issuer (live path or reconciler) |

The distinction the successor directive demands — *never signed* / *outcome
genuinely uncertain* / *signature definitely produced but persistence
unresolved* / *durably issued* — is carried by `failed` /
`signature_outcome_unknown` / `signature_known` / `issued` respectively, and
each is a separate durable state with its own writing principal.

## J. Issuance, retry and recovery evidence

| Scenario | Durable outcome |
|---|---|
| Normal issuance | `signing → signature_known → issued`; attempt `signing → signature_known → issued` |
| Signer returns, completion write fails | Row stays `signature_known`; the exact artifact is retained; retry re-serves it and **does not re-sign** |
| Signer request lost | The live path consults durable evidence before writing the weaker state, and only records `signature_outcome_unknown` when no `signature_known` exists |
| Retry after `signature_outcome_unknown` | A **new** attempt row is created; the earlier attempt's record is not rewritten |
| Key rotation between attempts | Each attempt retains its own `signing_key_id`; historical verification is unaffected |
| Process restart with a stale `signature_known` | The scheduled reconciler verifies the retained artifact against public key authority and promotes it to `issued`; an artifact that fails verification is counted in `invalid_signature_known_refused` and **left alone** |
| Process restart with a stale `signing` | Reconciler moves it to `signature_outcome_unknown` and marks the attempt likewise |
| Stale `authorized` | Reconciler moves it to `failed`; no attempt row is created |
| Live issuance racing the reconciler | Observed convergence to `signature_outcome_unknown` with the attempt row preserved (`c17_live_issuance_race_converged=signature_outcome_unknown`, `race_attempts=1`) |

## Q. What is not claimed

**The single load-bearing gap.** This corrective does **not** demonstrate the
successor directive's Plane-2 conduction requirement end to end. The gap is
narrower and more actionable than "ingress is absent", and it is worth stating
exactly, because the fix is a join rather than a build:

* `backend/tests/test_b23_p6_end_to_end_closure.py::test_b23_p6_signed_webhook_
  to_confirmed_api_downstream_closure` already conducts a real HMAC-signed
  Shopify webhook through real signature verification, real
  `webhook_ingress_identities` persistence, the production natural-dispatch
  path, the real Postgres broker and a real `b23_match_engine` worker, into a
  real `b23_match_verdicts` row — and then confirms it by calling the
  **production** `transition_stale_provisional_to_confirmed`, with the harness
  controlling only the clock, never the transition. That is a valid
  external-stimulus-to-deterministic-truth conduction proof.
* `b2-5-p13-c9-positive-confidence` already conducts a verdict confirmation
  through invalidation, the planner, the dedicated publisher, the real broker,
  the shipped Bayesian image, real four-chain PyMC sampling, diagnostics,
  confidence, Trust, signing and public JWKS verification, with `fit_id`
  identity asserted into the returned envelope.
* **No single job makes the verdict the webhook produced the verdict the Trust
  chain consumes.** The two halves are proven in different jobs over different
  records, which is precisely the disjoint-universe substitution the successor
  directive's §12 RC-XVIII-COMP-06 predicts.

Under the directive's evidence-admissibility law (§6), the P13 composition
proof's own starting authority is therefore still harness-written, which makes
gate `XVII-G` **FAIL-MANDATORY-PROOF** and gate `XVII-P` **FAIL-PROOF**.

What is true, and what is not:

* Every stage **below** the deterministic financial fact conducts, with asserted
  identity, through production-equivalent artifacts. That includes the real
  planner, the real dedicated publisher principal, the real Postgres broker, the
  shipped Bayesian image running real four-chain PyMC sampling, the real
  confidence projection, the real Trust builder, a real separate signer process
  holding the only private key, real Ed25519, real durable lineage under
  least-privilege principals, and real public JWKS verification.
* Every stage **above** it conducts too, in its own job.
* Therefore the claim "this signed TrustEnvelope's revenue figure came from a
  real external commerce event" is **not** proven by this corrective, because
  the two conducting halves are never the same causal universe. The claim "this
  signed TrustEnvelope's revenue figure came from *this* deterministic financial
  record, through a real posterior, under real signing authority, with durable
  truthful history" **is**.
