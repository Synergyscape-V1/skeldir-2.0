### 1(a) The property this phase must guarantee

**P-XXIV — Sovereign Financial Truth and Historical Conservation** (directive §3).

For every supported production execution and for every committed financial state:

> An authoritative financial result may be created or consumed only when its
> provider evidence, event meaning, canonical scope, financial transformations,
> correction history, historical witness, and current authority are independently
> defensible under the applicable policy.

Equivalently: **no reachable combination of in-scope operations may give an
unsupported financial fact the same authority as a legitimately derived one.**

The property has two inseparable obligations:

- **Boundary component (§3.1).** An in-scope actor cannot make false financial
  history authoritative by coherently changing ingress identity, verdict money,
  attribution money, supersession records, observations, the witness journal, the
  witness key or genesis, the custody checkpoint, currentness flags, scope-policy
  interpretation, or downstream projections — including combinations of those
  operations.
- **Breadth component (§3.2).** A legitimate provider event or correction must reach
  its correct supported consumer outcome across every supported provider, every
  governed event/lifecycle class, all four canonical dispositions, all supported
  rail/currency/reference/window combinations, inherited historical data, successive
  legitimate corrections, every downstream reader on one cohort, and complete
  signed and independently verified end-user consumption. A system that refuses
  everything fails.

**Historical distinguishability (§3.3).** World A (authentic history, legitimate
corrections, independently preserved historical authority) and World B (coherently
reconstructed representations conflicting with the independently established
original history) must produce opposite, independently verified outcomes through the
real consumer surface. If both worlds earn the same unqualified deterministic
financial acceptance, the property fails; if World A cannot progress to a usable
result, the property also fails.

The directive's positive counterpart governs every boundary fix: every legitimate
financial correction must advance independently defensible historical authority and
become consumable through the supported production path, without destroying earlier
history or making authority depend on manual repair.

#### Required authority-reach conclusions carried into the falsifier ledger

1. Verdict money is writable by `app_worker` today; the ledger trigger derives
   authority from that update. The correction path must be a governed caller, not an
   arbitrary UPDATE, and the final consumer must detect a coherent rewrite that
   suppresses the ledger (Report 72 A6/A10/A12).
2. The witness append is not atomic with custody: the journal is durable before the
   custody fork guard raises (Report 72 A3/A8); an unchanged-ledger refresh therefore
   cannot be a journal append at all.
3. The builder's verification root is deployment configuration (public-key path and
   genesis env). An actor with configuration/filesystem reach can replace both the
   journal and its root and obtain issuance (Report 72 A1/A5). The root must be
   externally anchored to the compiled artifact, and rotation must require the old
   root's authority.
4. The custody record is optional in the builder (`load_custody() is None` skips the
   check) and no independent record says a later commitment ever existed (Report 72
   A5). Absence must be distinguishable from first provisioning.
5. Source-money conservation compares mutable rows to each other (Report 72 A6).
   Detection requires an independent authenticated-source commitment retained outside
   the maintenance principal's reach.
6. The Trust envelope does not publish the money value (Report 72 B9/B12), so a
   machine consumer cannot reconcile the financial figure.
7. Provider terminal lifecycle evidence (Stripe `failed`, PayPal `denied`) is not
   consulted at the admission boundary, and unsupported currency/timestamp paths
   leave ungoverned state (Report 72 A9/B2/B7).
8. P2 normalization has more than one authority (`woo` vs `woocommerce`) and the
   fourth disposition is not persisted or machine-consumable (Report 72 B3/B4).
9. Rollback drops and re-mints the authority universe, orphaning retained signed
   history (Report 72 A11/B11).
10. No shipping caller invokes the correction kernel; the observer can sign a
    checkpoint only in a direct-kernel test (Report 72 A2/B10).

### 1(c) The honest path — full input space, inherited state, one cohort, real consumer journey

The honest path is the complete positive world the property requires, not the
previously demonstrated Stripe/Shopify subset.

1. **Inputs.** Every supported provider (Stripe, Shopify, PayPal, WooCommerce);
   every contract-defined event/lifecycle class (creation, update, successful
   payment, settlement where governed, refund, void, cancellation, failure, denial);
   every governed rail/currency/reference; integer-minor money; UTC half-open
   windows; malformed, unsigned, stale, future, unsupported-currency, and
   unsupported-rail inputs.
2. **Inherited state.** EMPTY→XXIV; each materially distinct predecessor generation
   (including data-carrying XXIII→XXIV); supported downgrade and re-upgrade with
   retained signed history; incompatible binary/schema pairs; witness recovery.
3. **Conduction.** Real signed ingress → provider authentication → relay → broker →
   `app_worker` → B2.3 consequence → P2 canonical classification → historical
   witness → source-money authority → TrustEnvelope construction → signer →
   independent signature verification → machine-readable financial result.
4. **Corrections.** A natural, shipping correction caller (API or worker or
   scheduler, not a direct kernel script) produces three or more successive
   legitimate corrections; the observer advances checkpoints naturally; an
   unchanged-ledger interval refreshes freshness without appending history; restart
   and recovery preserve authority without manual repair.
5. **One cohort, every reader.** One committed cohort containing valid, corrected,
   excluded, unresolved, historical, and non-current cases is read through B2.3, P2,
   batch, coverage, P3 eligibility, Bayesian read-only projection, API, Trust and
   export; all agree on source identity, money, currentness, semantic law,
   provenance, qualification, and refusal reason.
6. **End-user journey.** Fresh tenant and credential → signed ingress → auth root →
   relay/broker → B2.3 → P2 → witness → current source-money authority → envelope →
   actual signature → independent verification → machine-readable amount → governed
   source/history change → correctly requalified second read. All steps belong to
   the same causal journey; no mock boundary, seeded downstream truth, or manual
   journal repair substitutes for a hop.

**Adversarial counterpart (the negative world).** An independently retained original
provider reference is established first. Then an in-scope maintenance or runtime
principal coherently rewrites ingress, verdict, attribution, observations, ledger,
journal/custody and projections within its reach. The final machine consumer must
refuse or explicitly qualify the result, and the mandatory proof must turn RED for
the right reason. The independent reference stays outside the constrained
principal's unilateral reach.
